## 🔒 この表の使い方（設計ルール）

### 起きた事故

つまみの卓上治具（2026-08-02・[PRINT.md](PRINT.md) 3回目）で3件やった。

| 起きたこと | 何を間違えたか |
|---|---|
| コネクタのスロット位置が外れ、手加工で窓に開け直した | **説明書を流し読みして、ピンの位置とピンヘッダーのサイズを考慮し忘れた** |
| 軸がブリッジの穴に入らず、削って通した | 凸は太る・穴は縮むという**印刷側の補正**を穴の設計値に入れ忘れた |
| スタンドオフが2本折れた | 長穴の向きの肉厚を**計算していなかった**（0.3mmしか無かった） |

**3件を一つの教訓にまとめない。** 原因が別々で、まとめると薄まる。
1件目は**在った情報を読み落とした**（ユーザーもピンヘッダーが立っていることを
説明していた）。2件目は**補正を入れ忘れた**。3件目は**計算しなかった**。
どれも「難しくて分からなかった」ではない。

⚠ **以前ここには「3件とも現物を当てずに数字を置いた」と書いてあった。**
事故を認識論の話へ格上げした書き方で、実際より上品にしていた。書き換えた
（2026-08-03・ユーザーの指摘）。

### 下の格付けが効く範囲

**上の3件には効かない。** 格付けが効くのは別の型 — **公称値をそのまま設計値にする**
事故（外形は📄で足りるが、穴の位置に使うと外す）。上の3件は、**在った情報を
使わなかった**型。**同じ表では防げないので、分けて持つ。**

⚠ **そして 2026-08-03、同じ読み落としをこの表を書きながらもう一度やった。**
公式ページに両面のピンアウト図があるのに、テキストの仕様表だけ見て
「面の割り当てはネットに無い」と書いた（下で訂正済み）。**一次情報を開いて、
最後まで見る。** 仕様表・図・写真は別々の情報で、表だけ読むのは流し読みと同じ。

### だから、数字に格付けを付ける

| 記号 | 意味 | 設計で許されること |
|---|---|---|
| ✅ | **実測** — 手元の現物で測った・嵌めて確かめた | **穴を置いてよい** |
| 📄 | **カタログ** — メーカー／販売ページの公称値 | **外形の当たり（入るか／どのくらいの箱か）まで**。穴は置かない |
| ⚠ | **推定** — 誰かが決め打ちした値。写真からの読みも含む | 設計に使うなら**長穴・窓・逃がし**にする |
| ⬜ | **未取得** | 使わない |

> **📄と⚠の上に、位置の決まった丸穴を置かない。**
> 逃げ方は治具でもう出ている — 位置が怪しければ**丸ごと窓にする**（基板の下を全部開けた）、
> ピッチが怪しければ**長穴にする**（±1mm 吸収）。**手加工で開け直すより、
> 最初から開けておくほうが安い。**

### 📄 を拾うときは一次情報から

⚠ **ここには一度「XIAOの外形は出どころによって 21×17.5 / 21.5×17.5 / 21×17.8 と
食い違う」と書いた。誤り。**
[Seeed の仕様表は **21 × 17.5 mm** の一つだけ](https://wiki.seeedstudio.com/xiao_esp32s3_getting_started/)。
食い違って見えたのは、検索結果に出たまとめサイトや販売店の記事を一緒に数えたから
（2026-08-03 訂正）。**公称値が当てにならないのではなく、公式を見ていなかった。**
ReSpeaker Lite の **35 × 86 mm** も同じで、公式の仕様表に最初から書いてある。

**📄 に採ってよいのは、メーカーの wiki・データシート・製品ページだけ。**
検索結果の要約や転載記事は数に入れない。

### 0.6 ハブ基板は推定せず、穴割りから生成する（2026-08-15）

🔴 **穴割りが分かっているのに、AI はハブ基板を「18mmの赤い箱」で代用し続けていた**
（ユーザー指摘「穴割が分かっている時点で正確にモデリングできるのでは」）。**そのとおりだった。**

```bash
python hardware/parts/gen_hub_board.py     # relay_board.html → hub_board_parts.scad
```

🔒 **手で転記しない。**正は [relay_board.html](../hardware/parts/relay_board.html) の `initialLayout()` で、
穴割りを直したら流し直す（`respeaker_lite_parts.scad` と同じ方針）。**部品17個・口7個**が実位置に載る。

⭐ **生成した瞬間に、推定の誤りが2つ出た。**

| | 推定していた値 | 実際 |
|---|---|---|
| ハブ層（横出し） | 8.0mm | 🔴 **13.6mm**（板1.6＋リレー10＋半田面2） |
| ハブ層（立てる） | 27.0mm | **28.6mm**（板1.6＋口25＋半田面2） |

🔒 **最高点はヘッダの向きで入れ替わる。**立てれば**口が25mm**で断然の最高点、
横出しにすれば口は寝て⚠約6mmになり、**リレーの10mm**が最高点になる。
🔴 **13.6mm のうち 10mm はリレーで、ヘッダを寝かせても減らない。**

⚠ **AI はここに「最高点はピンヘッダ(8.5mm)ではなくリレー(10mm)」と書いた。誤り**
（2026-08-15・ユーザー指摘）。**8.5mm は裸のヘッダで、ハウジングを忘れている。**
25mm という数字を自分で記録した後に、同じ忘れ方を2回している。
🔒 **口の高さは、必ずハウジングが挿さった状態で数える。**

### 🔴 穴割りが鏡像だった（2026-08-19）

**ユーザー指摘**「中継基板のコネクタの位置が実際と違う。鏡面になってないかこれ。
ハンダ面に部品が乗ってる」。**そのとおりだった。**

`relay_board.html` は**部品面**を描いていて、SVG の y は下向きなので画面では **行A が上**。
`gen_hub_board.py` は行A を **Y 小**に置いていた。SCAD で部品面（+Z）から見下ろすと
Y は画面の上へ伸びるので、**同じ面を見ているのに上下だけが反転**する。列はどちらも
左が列1なので、**回転では戻らない鏡像**になっていた。

🔒 **HTML の画面の上 = SCAD の +Y。** 生成器の `hole_xy()` で行を反転して直した。

さらにユーザー指示で **板は筐体へ 180度 回して載せる**（`ROT180`）。鏡像を直しただけだと
口が前後そっくり入れ替わり、XIAO が背面・PWR が前面になって**テストするまでもなく当たる**ため。
⇒ 生成器は**載る向き**で座標を出す。`HUB_ROT180` を `hub_board.scad` の `hub_dir()` が読み、
口の向きも一緒に回る。**座標だけ回して向きを回さないと、口の向きだけが嘘になる。**

⭐ **鏡像の修正と180度回転は打ち消し合うので、旧モデルとの正味の差は「左右の反転」だけ。**
Y は10口すべて不変で、X が `74 - x` になった。**同じ辺に居るが、左右が入れ替わっている。**

| 口 | 旧 X | 新 X |
|---|---|---|
| PHIN / PHOUT（ReSpeaker・スピーカー） | 4.0（左辺） | **70.0（右辺）** |
| AS5600（つまみ） | 64.9（右辺） | **9.1（左辺）** |
| BTN2（会話ボタン） | 67.5（右辺） | **6.5（左辺）** |
| PWR（PowerBoost） | 9.1〜16.7（背面の左） | **57.3〜64.9（背面の右）** |
| XIAO | 37.0〜52.2 | 21.8〜37.0 |
| OLED / INA | 42.1〜49.7 | 24.3〜31.9 |
| TOGGLE | 21.8〜24.3 | 49.7〜52.2 |
| REED | 29.4〜31.9 | 42.1〜44.6 |

🔴 **これで筐体の配線は全部引き直しになる。** とくに `case_v2.scad` が
「ハブの PWR の口が板の左後ろにあるので PowerBoost を左へ入れ替えた」と書いている根拠が
**反転した**（PWR は背面の右になった）。

⚠ 生成器そのものも2回こけた。`fn:'D3'` `fn:'D2'`（XIAOのピン名）を穴名として拾って
**XIAOの口が7本ではなく9本**になり、OLEDのラベルの `"` が SCAD の文字列を壊した。
**どちらも「口の本数を数える」だけで見つかる**ので、生成器は本数を必ず出力すること。

### 🔴 OpenSCAD の警告を捨てない（2026-08-15）

**箱詰めスタディでハブ基板が原点に置かれ、絵が滅茶苦茶になった。**原因は
`use <hub_board.scad>` が**モジュールと関数しか取り込まず、変数を取り込まない**こと。
呼ぶ側の `HUB_SOLDER` が undef になり、`translate([2, 40.125, undef])` が**丸ごと無視された。**

🔴 **OpenSCAD はこれを WARNING で2行はっきり出していた。**
AI が出力を `grep -E "ECHO|ERROR"` で拾っていたため、**自分で警告を捨てていた**
（ユーザーが OpenSCAD の画面を見て発見）。

| 🔒 決めごと | |
|---|---|
| ビルド出力は **`grep -Ei "warning\|error"` で必ず見る** | ERROR だけ拾わない |
| **外に出す値は変数でなく関数にする**（`hub_solder()`） | `use` で変数は渡らない |
| 絵と寸法計算を食い違わせない | `S_CORRIDOR=0` のとき横の通り道を描いていた |

⚠ **外寸の数字（455.7cm³）は変わらなかった。**寸法は定数から計算していて、
描画位置とは独立だったため。**壊れていたのは絵と、絵による検証のほうである。**

### 🔒 唯一の設計変数は「25mm をどの軸で払うか」

**コネクタ1個は約25mm要る**（上の1.5節）。**向きを変えても数字は同じ**なので、
ヘッダの向きは「その25mmを高さで払うか、基板面で払うか」の選択でしかない。

⚠ **この節には一度、行A の通り道しか入れず、ハブ層も推定値(8mm)で置いた表があった。
2026-08-15 に2回とも訂正したので削除した。**⚠ **[relay_board.html](../hardware/parts/relay_board.html) を
開かずに書いたため、行S に口が4つ集中しているのを見落としていた**（2026-08-15・ユーザー指摘）。
行S を入れ直すとこうなる（OLED 20mm のとき）。

🔒 **2026-08-15、ハブ基板を推定値でなく実物のモックに置き換えた**
（[hub_board.scad](../hardware/parts/hub_board.scad)。穴割りから自動生成・下の 0.6節）。**数字はこうなった。**

| ヘッダ | 行S の行き先 | 外寸 | 体積 | 高さ |
|---|---|---|---|---|
| **横出し** | 全部**下段へ降りる**（下限） | 90 × 98 × **51.6mm** | 456cm³ | ⭐ |
| **横出し** | 全部**パネルへ出る**（上限） | 90 × 121 × **51.6mm** | 563cm³ | 長辺が痛い |
| 立てる | （通り道は要らない） | 90 × 75 × **66.6mm** | 450cm³ | ❌ |

🔴 **横出しの優位は「高さだけ」に縮んだ**（51.6 対 66.6mm）。**体積では並ばれている**
（456 対 450）。急所は高さ（[ARCHITECTURE.md](ARCHITECTURE.md) 223行）なので**方向としては横出しのまま**だが、
⚠ **「横出しで確定」と2回言ったのは、どちらも根拠が足りていなかった。**

⚠ **なぜ悪化したか: ハブ層が 8mm ではなく 13.6mm だったから**（内訳と誤りの経緯は 0.6節）。

⬜ **決め手は行S の内訳である。** PowerBoost(4) と INA226(4) は**箱の下段にある部品**なので
線は下へ降り、通り道は要らない。トグル(2)・リード(2)・会話ボタン(2) は**パネルへ出る**。
**この6本をどう逃がすかだけが残った判断で、それが決まるまで横出しは確定にしない。**

⚠ **一度ここに「横出しなら OLED の疑いはほぼ効かない」と書いたが、ハブ層が 13.6mm に
上がったことで OLED の塔が再び床(34mm)を超えた。効かなくなるとは言えない。**（2026-08-15 訂正）

⚠ **AI は「向きに関係なく要る数字」と書いた直後に、ヘッダ高さを別の未知数として
測定を要求した**（2026-08-15・ユーザー指摘）。**同じハウジングに同じ線が挿さるのだから
同じ25mm。**同じ物を2回数えていた。→ `CONN = 25.0` の1変数に統合した。

### 🔒 この配置は好みではなく、3つの制約から一本道で出ている

| | 制約 | そこから決まること |
|---|---|---|
| 1 | **マイクは上か正面を向く**（塞ぐと音が死ぬ・ユーザー 2026-08-15） | 天面は OLED が占めるので、**マイクは正面**しか残らない |
| 2 | マイクは**マイク面の両端**にある（U4/U5・[RESPEAKER-LITE.md](RESPEAKER-LITE.md)） | → **ReSpeaker は立てる**（同文書 240行の結論と一致） |
| 3 | ハブ基板(74×52) と OLED(70×48) は **footprint がほぼ同じ** | **必ず重ねる。** 横に並べると Y が30mm伸びる |

⭐ **`opt` では高さの支配が「OLEDの塔」から「立てた基板の34mm」に移る。**
これは**物理的な床**である。マイクを正面に向ける限り基板は立ち、34mm より低い箱は作れない。

🔴 **候補A（全部平置き）は捨てた。マイク面が箱の底を向いていた。**
[RESPEAKER-LITE.md](RESPEAKER-LITE.md) は最初から「基板は立てる」と結論していたのに、
箱詰めのときに参照しなかった。→ `mic_path()` で**音の通り道を可視化**して再発を防ぐ。

⚠ **この数字を「箱の大きさ」として引用しないこと。** まだ足りていない。
① **つまみが入っていない**（再設計中・[KNOB-ENCODER.md](KNOB-ENCODER.md)）
② ハーネスは **行A（ReSpeaker行きの7本）の1本ぶんしか入れていない。**
   列1・列27 の口の通り道は未計上（他の部品の隙間と共用できる見込みだが、未検証）
③ 逆方向の余地として、**充填率は39%**（部品191cm³ / 箱484cm³）。まだ詰められる

### ⚠ StackChan との比較は、体積ではなく高さで見る

🔴 **下の `opt` の行は 2026-08-14 の箱詰めスタディで、実際に作った筐体ではない。**
筐体 v4 で測り直した確定値は [ARCHITECTURE.md](ARCHITECTURE.md) の
「筐体 v4 で測り直した比較（2026-08-27）」にある（面積 6,498mm² ／ 高さ 52.95mm ／ 体積 344cm³）。
**高さは 40mm では収まらなかった**（`opt` はつまみも外皮の厚みも入っていない）。

| | 設置面積 | 高さ | 体積 | 電池 |
|---|---|---|---|---|
| StackChan | 3,807mm² | **61.5mm** | 234cm³ | ❌ 含まない |
| katanori `opt`（🔴 過去のスタディ） | 6,581mm² | **40mm** | 263cm³ | ✅ 含む |
| **katanori v4（実物）** | **6,498mm²** | **52.95mm** | **344cm³** | ✅ 含む |

🔒 **[ARCHITECTURE.md](ARCHITECTURE.md) 223行のとおり、肩に載せる物の急所は高さである。**
体積で1.1倍・面積で1.7倍だが、**高さは3分の2に収まっている**（薄く長い板になるという読みどおり）。
⚠ **ただし体積の比較はそもそも公平ではない。** StackChan の234cm³は電池を含まず、
katanori 側は電池・PowerBoost・XMOS まで入れた数字である。

**約束:**

1. **測っていない部品はモックに書かない。** 仮の箱を置くと、それが事実として使われる
2. 外形だけでなく、**コネクタ・ピンヘッダー・線の曲がり**まで箱にする
3. 新しい寸法を測ったら、**この表とモックの両方**を更新する
4. 筐体を刷る前に、`respeaker_envelope()` などを `difference()` して**削れないことを確認する**

## 4. 印刷の補正（穴を開けるときに必ず足す）

**寸法表と別に持たない。** 部品の寸法を筐体の穴に変換するのはここ。

|---|---|---|
| 穴の縮み | **約 0.1mm** | 穴系の**設計値に足す**（`SHRINK`） |
| 凸の太り | **約 0.1mm** | 軸などの外径から引く／隙間の見積りに入れる |
| 回る嵌合の遊び | **直径 +0.25mm**（✅2026-08-05 実測ばっちり） | 🔒 **入口逃がしとセットで成立**。逃がし無しの旧実測が「0.25では通らない」だったため一時0.40まで開けたが、ガタが出た（`BORE_CLEAR`） |

| 板バネ | 🔒 **レジン①では作れない** | 刷った直後は戻るが、**1日半で全数破断**した |

⚠ **設定を1つでも変えたら、この列は全部取り直し。**
⚠ **レジン①は経時で脆い。** 樹脂にネジを切らず、**M2は貫通＋ナット**にする。
（根拠は**板バネ試験1件だけ**＝薄肉0.4〜0.8mmを二次硬化後・1日半経過で曲げた話。

## 4.6 見せる部品を刷るなら、レジン②へ（段階4が要る）
