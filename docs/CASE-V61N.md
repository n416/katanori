
`skin`・`all`・`explode` は MAT に追従する（nylon なら底パーツ＋蓋の 2 部品（8 章）。explode は底パーツを置いたまま、蓋は小組ごと上へ・PCB と電池は左の窓から外へ・ReSpeaker と OLED はライザーごと上へ）。

仕組み（2026-09-16）: case が `$mat = MAT;` を置き、`$` 付きの変数が呼び出しの連鎖を伝わる性質で `use` した部品
（つまみ・会話ボタン・スピーカー）の先頭の代入にも届く。部品ファイルは include の直後に `$mat = is_undef($mat) ? "resin" : $mat;` を持ち、
単体で開けば resin、`-D '$mat="nylon"'` で nylon、case から use されれば case の値になる。case の assert が食い違い（`-D $mat=` だけ渡した等）を捕まえる。
🔴 2026-09-15 までは `parts/mat.scad` の `MAT = "resin";` を書き換える方式だった（-D が use 先に届かないため）。書き出しスクリプトはその行を一時的に書き換えていたが、いまは -D で渡す。

部品側も同じ `nylon()` を読む: `parts/knob_v61.scad`・`parts/btn_v61.scad`・`parts/spk_v61.scad`
（前者 2 つは v5 と共用の knob_v5 / btn_v3 の写し。v5 は触らない）。

## 1. なぜ形が違うのか

v6.1（レジン）が板 6 枚なのは、**寝かせて刷る・反る・支柱の跡を面に出さない**の 3 つが理由だった。
MJF（粉の中で焼く）ではその 3 つが消えるので、**床＋4 壁を 1 部品、天板だけ蓋**にした。

~~中身を入れる口は上の 1 か所だけでよい。ReSpeaker と PCB はどちらも幅 82.02 で、箱の内寸との
余裕が左右合わせて 1.43mm しかなく、**上下からしか入らない**ため。~~
🔴 **これは間違いだった（2026-09-16・ユーザー「ナイロン組み立て不能では？」）。** 上からしか入れられない箱に対して、最後に横向きに動く物が
3 つあった（充電の USB-C・XIAO の USB-C・OLED のダボ）。床＋4 壁の一体シェルは組めない。直した形は 8 章。

つまみ・スピーカー・会話ボタンの小組は今までどおり天板の上で完結する（深さ 50 の箱の底から
工具を入れる作業にしない）。だから天面が蓋である必要がある。

## 2. 刷り分け

| 部品 | 材料 | 体積 | 理由 |
|---|---|---|---|
| 底パーツ（床＋前・後ろ・右の壁＋左の壁の帯） | MJF PA12 | 26.75cm³ | 大きい・反りと支柱が問題になる（8 章の分割・2026-09-16） |
| 蓋（天板＋左の板） | MJF PA12 | 17.41cm³ | 同上 |
| スピーカーのバスタブ | MJF PA12 | ― | 公差が要るのは六角だけ（呼び ＋0.5） |
| 会話ボタンの押し子・バスタブ | MJF PA12 | ― | 動く嵌めは片側 0.40 ＝ 直径 0.80 で MJF の下限 0.76 を満たす |
| つまみ一式（島・つまみ・軸） | MJF PA12 | 4.91cm³ | E リング 2 枚で公差を吸収する（下） |

**全部 MJF。レジンで刷る部品は無い。**大きい 2 部品で 44.2cm³ ≈ 44g（レジンの 6 枚は 61.3cm³ ≈ 67g）。

つまみが MJF に乗るのは 🔒 ユーザー案「軸を大きくしたうえで、溝も広げて 2 個入れればいい」による。
軸は 7 のまま（呼び 6 は軸 φ7 に溝 φ6 を切る規格どおりの組み合わせ）で、溝を 2 枚ぶんに広げた。
つまみ側で MJF に合わせて動かした数字は 3 つ:

| | レジン | MJF | 理由 |
|---|---|---|---|
| E リングの溝 | 幅 0.95・径 6.0・1 枚 | **幅 1.90・径 5.85・2 枚** | 幅は枚数で、径は狙いを 0.2 細くして安全側へ |
| 軸受けの遊び | 0.25 | **0.80** | 軸も島も ±0.3 に振れる。0.25 だと最悪 −0.35 で固着 |
| 磁石のポケット | φ4.10（圧入） | **φ4.50 ＋ 接着** | 4.10 だと細い側 3.8 で φ4 の磁石が入らない。入れて瞬間接着剤で留める |

### 5.4 稜の丸みが R 1.6 に縮んでいた（2026-09-16 に直した）

### 9.6 ナットを回すと薄肉が出る件（2026-09-16 に解消）

`S_NUT_ANG` を変えるたびに天板のスピーカーの座に薄い刃が出ていた。原因は 2 つあった。

**① 確かめる道具のほうが、角度以外で答えを変えていた。**
`case_v6_1.scad:63` は `$fn = 48`、`parts/spk_v61.scad` には無く、薄肉落としの `offset()` も `$fn` を渡していなかった。
そのため**呼び出し側で多角形が変わり**、同じ `S_NUT_ANG = 20` でも 部品単体 `part="deck"` は 🔴 0・天板は 🔴 1 になっていた。
→ `spk_v61.scad` に `S_FN = 48; $fn = S_FN;` を置いて揃えた。

**② 直線の手と曲面の縁を、同じ半径から立てていた。**
手の板 `spk_hang_arms` の内の面は座の輪郭に**接する直線**（x = S_R_I）。縁 `spk_rim` の内の面は**同じ半径の曲面**。
だから縁は手の内の面より内へ `R − sqrt(R² − y²)` だけ出る（手の縁 y = ±3.3 で **0.73**）。
その裏にナットのポケットの空が来ると、厚さ 0 → 0.73 の楔になる。**角度で深さが変わるので出たり消えたりしていた。**
→ `spk_rim_relief()`: **手のまわりの縁を丸ごと落とす**（薄くするのではなく無くす）。位置出しは手の板 2.8 厚が持つ。
窓は手より `S_RIM_GAP` 0.6 広い（同じ幅だと面が重なって厚さ 0.00 の板が出る）。半径方向は縁の外まで通す。

掃引（`part="deck"`・`$fn=48`・5° 刻み）: **0〜105° で 🔴 0**。110° より先は両方の手がぶつかって部品が分裂する範囲なので設計として成立しない。
当たり検査 16 項目は 8.3 の表と全一致。レジンの 16 項目も変更前と同一。

🔴 やって駄目だった直し方（繰り返さないこと）:
- 断面を `projection(cut=true)` で取り、「縮めて膨らませて」薄い所を削る … 凸の角が全部丸まるので 🔴 が 20 枚に増える
- 縁の逃げを手と**同じ幅**で切る … 面が重なって厚さ 0.00 の板が 9/20 の角度で出る
- 逃げの深さを `sqrt(R² + y²) − R` で計算する … **式が逆**。正しくは `R − sqrt(R² − y²)`。浅いと端に三日月が残る

### 9.8 入れる道の掃引を「通過点の並び」に書き直した（2026-09-17 夜）

🔒 ユーザー「本来であれば対象物をどう移動させるかのパスを定義してあたりを出すべきでしょ」
「入れられないかを判断する道具は必要だよ？ 当たり前だけど」「そのクソみたいな機能のツールはいらないということ」。

**何が駄目だったか。** 道具は `sweep_x` と `sweep_z` の 2 本しか持っておらず、**X と Z の平行移動しか書けなかった**。
そのため「前へずらして入れて、下ろしてから後ろへ押して口に挿す」という実際の動きが書けない。
充電の USB-C を後ろの縁（ハッチ）へ移した 2026-09-17 以降、板の縁から 1.3 出た胴が
**横差しの間じゅう後ろの壁の中を通る形**で数えられ、`path_hub` は 51.4mm³ を出し続けていた。
入る動きなのに「あたってます」と言い続ける道具で、しかもその処遇をユーザーに判じさせていた。

**直し方。** 道の 1 点を **`[dx, dy, dz, 回し（度・Z 軸まわり）]`** で持ち、点と点のあいだを n 等分して当てる
（`pose_lerp` / `at_pose` / `sweep_pose`）。これで Y のずらしも斜めも書ける。回す中心は物ごとに渡す。

```
//                dx          dy   dz        rx ry rz
PATH_HUB = [[-95, -pcb_fwd(), PCB_LIFT, 0, 0, 0],   // ① 前へ 1.8 逃がし 3.5 上げて左の窓の外
            [  0, -pcb_fwd(), PCB_LIFT, 0, 0, 0],   // ② 右へ滑らせて中へ
            [  0, -pcb_fwd(),        0, 0, 0, 0],   // ③ 柱の頭まで下ろす
            [  0,          0,        0, 0, 0, 0]];  // ④ 後ろへ 1.8 押して USB-C を口へ挿す
```

**回しは 3 軸ある。**（🔒 ユーザー「これ、入れる物体の角度とかも変えられるの？」「3 軸の変更は必要だし……
特定位置で固定してから回すって動きがあるわけだ」）。最初は Z 軸まわりの 1 つしか持たせておらず、
平面で首を振れるだけで**傾けられなかった**。「斜めに入れる」は普通 X か Y 軸まわりに倒すことなので、
それが書けないと道具の意味が無い。回す中心 `c` は物ごとに渡す（既定は世界の原点で、傾けると物が遠くへ飛ぶ）。
板は `hub_c()`（板の芯）。

**刻みは決め打ちにしない。** 姿勢を n 個置いて union する以上、姿勢と姿勢の**あいだは見ていない**。
刻みより細い物はすり抜けて 0.00 が出る ── それは「入る」ではなく「置いた姿勢では当たらなかった」である。
板は 82mm あるので、芯まわりに **1° 回すだけで端は 0.7mm 動く**。回しを足すほど取りこぼしが増える。
⇒ 1 刻みで物のどの点も `SWEEP_STEP` より動かないよう、区間ごとに n を数える（`pose_move`）。
`SWEEP_STEP` は **1.5**（🔒 ユーザー「重すぎるんでやめてください」）。書き直す前の決め打ち（`path_hub` は 95mm を 60 で刻んで 1.58）
とほぼ同じ細かさで、`path_hub` は 10 秒。0.25 まで落として回しても **16 項目の値は 1 つも動かなかった**ので、
この板と蓋については粗くして失う物は見つかっていない。⚠ ただし「1.5 より細い物はすり抜ける」ことは変わらない。
怪しい所を詰めるときだけ 0.25 に落として回す（`path_hub` が 10 秒 → 120 秒）。
回したときいちばん動くのは端なので、**回す中心から端までの長さ r** を渡してもらう（弧の長さ r・Δθ）。板は `hub_r()` 45.7。

🔴 **`hull()` で隣の姿勢を繋ぐ手は使えない**（2026-09-17 夜に試して捨てた）。凸包なので**へこみが埋まる**。
蓋のような凹んだ殻でやると `path_lid` が 0.07 → **21327mm³** になった。厳密なのは Minkowski だが遅すぎる。
「平行移動なら hull は通り道そのもの」は**凸な物に限った話**である。

- `pcb_fwd()` = `usbc_out()` + 0.5 = **1.8**。数字ではなく式で置く。
  🔴 **関数にすること。** `PCB_HATCH_GAP` はこの行より下で代入されるので、変数だと `undef` になる
  （実際に踏んだ: 天板の窓が `undef` になって STL が書き出されず、**古いファイルの数字を読んで報告した**）。
- `part="path_hub_one"`（`-D PI_=<番号>`）で通過点を 1 つだけ置いて当てられる。どの段で入らないかを見る用。

**道具が直ったら本物を 1 件捕まえた。** 前へ 1.8 ずらした姿勢では、**J10（電池の口・板の裏）が自分の窓から外れて
電池ケースの天板を削っていた**（6.16mm³・世界 X 76.0〜80.5 / Y 24.7〜26.0 / Z 7.0〜8.2）。
窓は最終位置に合わせて開けてあったためである。⇒ `bat_case_j10_win()` の **−Y 側を `pcb_fwd()` ぶん広げた**。
旧の道具では Y へ動かせなかったので、この当たりは永久に見えなかった。

🔴 **「斜めに入れる」は使えない**（2026-09-17 夜。🔒 ユーザー「斜めに入れる道も一度試して、入るか見て」
→ 掃引が重く、測り終わる前に🔒「重すぎるんでやめてください」。**以下は測定ではなく図面の数字からの理屈**）。

| 案 | なぜ駄目か |
|---|---|
| 首を振る（Z 軸） | USB-C は板の X **43.012**、板の芯は X **43.0**。**回転軸の真上**なので何度振っても動かない。加えて内寸 82.66（`IN_X` 84.354 − `LW_X` 1.694）に板 82.024 なので遊びは 0.636。必要幅 `82.024·cosθ + 37.4·sinθ` が内寸を超えるのは **1° 弱**で、そもそも振れない |
| 倒す（X 軸） | 効きはする（15° で USB-C は約 1.5 前へ引っ込む）。だが**最後に口へ入れる一手が回転ではできない**。口は 9.54 × 3.86、殻は 8.94 × 3.26 で**片側 0.3 しかない**。回して戻すと殻の角が弧を描いてこの 0.3 を食う。⇒ 倒しても最後は **Y へまっすぐ押す**しかない |

最後にまっすぐ押すのなら、途中で倒す意味が無い。**前へ 1.8 逃がしたまま入れて押す**いまの道の方が動きが 1 つ少ない。

**検査 16 項目**（`python hardware/tools/stl_v61n.py --check`）: `path_hub` **51.9 → 0.00**。
他の 15 項目は 8.3 の表と全一致（書き直しの巻き添え無し）。
刻みを 0.25mm まで細かくしても値は 1 つも動かなかった（`path_oled` 0.51 / `path_rsp` 0.00 /
`path_bat` 86.82 / `path_lid` 0.07）。**前の粗い刻みが何かを取りこぼしていたわけではない。**
その 0.25 は時間が重すぎた（`path_hub` 120 秒）ので、常用は **1.5**（`path_hub` 10 秒）に戻した。
preflight（MJF）: 底パーツ・蓋とも **🔴 0・二重面 0・中身 1 個**。逃げの 0.4 の段も広げた窓も警告を足していない。

### 9.9 掃引を捨て、判定を距離クエリへ移した（2026-09-17）

🔒 ユーザー「道を通過点で書く形と 3 軸の回しの 0.25 刻みをやったら PC が固まりました」→「旧の掃引検査は削除」。

**なぜ固まったか。** `sweep_pose()` は姿勢を n 個 union して交わりの**体積を作る**。CSG のブーリアンなので
姿勢の数だけ面数が増える。`PATH_HUB` は道のり約 100mm あり、0.25 刻みで 400 姿勢。
`hub_unit()` は 28782 面なので、**1150 万面を 1 つのソリッドに合体**させようとしていた。
粗くすれば今度は姿勢と姿勢のあいだを見ていない。**この方式では「誤報か、重すぎるか」は原理的に解けない。**

**世の中の手**（調べは docs/COLLISION-SURVEY.md）。CAD の当たり判定で交わりの形を作る流儀は無い。
三角形を BVH に入れて**最短距離を mm で返す**（FCL・ROS/MoveIt の標準）。刻みは決め打ちにせず、
「いま d 空いていて、物の最大点速度が v なら d/v 進んでも当たらない」と保証しながら進む（Conservative Advancement）。
誤報はしきい値（clash tolerance）で落とし、体積ではなく**深さ**で判定する。

**移した形。** 形を作るのは OpenSCAD のまま、判定と動画だけ外へ出した。

```
python hardware/tools/sweep_chk.py hub rsp oled bat     # 検査
python hardware/tools/sweep_movie.py bat                # 動画（_tmp_sweep/bat.mp4）
```

| 道 | 旧（掃引・体積） | 新（距離＋厳密） |
|---|---|---|
| `path_hub` | 0.00 mm³ | 厚み 0.000 mm（同一平面の皮）→ **入る** |
| `path_rsp` | 0.00 mm³ | 厚み 0.000 mm（同一平面の皮）→ **入る** |
| `path_oled` | 0.51 mm³ | **0.512 mm³**・厚み 0.400・1.6×0.8×0.4 @ s=0.898 |
| `path_bat` | 86.82 mm³ | **86.818 mm³**・厚み 2.382・35×6×2.382 @ [15.2, 9.9, 0.5] |

体積は小数 3 桁まで一致した。新しい方は**道のどこで・どんな形で**当たっているかまで出る。
`path_hub` は距離 188 姿勢 1.8 秒 ＋ 厳密 13 回 ＝ **11 秒**（旧は 0.25 刻みで PC が固まった）。4 本まとめて 48 秒。

**`SWEEP_STEP` は無くなった。** 空いている距離から刻みを出すので、広い所は 1 歩で飛び、狭い所だけ細かくなる。
「1.5 か 0.25 か」を人が選ぶ問題も、「刻みより細い物をすり抜ける」穴も消えた。

**誤報の落とし方。** 隙間 0.05mm 以下を接触として扱い、そこで厳密な交わりを取って**主軸で測った厚み**を見る。
0.01mm 未満なら同一平面の皮 ＝ めり込みではない。`path_hub` の接触は 13 姿勢すべて厚み 0.000 の平面で、
板の裏が柱の頭に載っているだけだった。**体積では区別できない**（5mm³ は「深さ 0.01 × 面積 500」かもしれない）。

**外した物。** `case_v6_1.scad` から `sweep_pose` / `pose_move` / `SWEEP_STEP` / `path_*` /
`path_*_one` / `path_*_show` を削除。`stl_v61n.py --check` の 16 項目は **11 項目**になった
（残り 11 の値は撤去の前後で全一致）。`PATH_*`・`at_pose`・`world_for_*`・`lid_flexed` は新しい道具が使うので残す。

**まだ載っていない。** 蓋（`path_lid`）は**たわむ**ので、剛体を前提にした新しい道具に乗らない。
道（`PATH_LID`）とたわんだ姿勢（`lid_flexed()`）は `case_v6_1.scad` に残してある。
⇒ **いま蓋の入れる道は誰も見ていない。**
