# 話しかけ・会話参加のロードマップ

## 目指すもの

**最終目標**: 複数人の会話にそばで混ざれるロボット。

そこへ至る道は2本ある。混ぜて考えると設計を誤る。

| 軸 | 内容 | いま |
|---|---|---|
| A. 呼ばれて応じる（受動） | 話しかけられたら反応する | **レベル0（ボタン）＝仮OK** |
| B. 自分から入る（能動） | 会話を聞いて頃合いで入る | 未着手（最終目標） |

**土台は共通**。どちらも「常に聞く → 安く文字にする → 判断する → 必要なときだけGeminiに繋ぐ」
の二段構えで動く。Aで作るものはBでそのまま効くので、順にやれば無駄がない。

## 決まっていること

1. **レベル0（ボタン）を仮OKとする。** 確実に動く。ここで止まっても製品として成立する
2. **決まった呼び名を覚えさせる方式は採らない。** 呼び名を自由に変えたいという要件と両立しない
3. **入力は1つに絞らない。** 確信度の違う入力を足し合わせる（下表）
4. **迷ったら聞き返す。** 「私ですか？」と返せるので、各入力は完璧でなくてよい

### 確信度と反応

| 確信度 | 例 | 反応 |
|---|---|---|
| 確実 | ボタン、遠隔ベル、叩く | すぐ会話を始める |
| 強い | 声 ＋ 目線 | 短く返事をして始める |
| 弱い | 声だけ | 「私ですか？」と聞き返す |
| なし | 周囲の会話、テレビ | 黙る |

## 各項目のメモ

### 叩いて起こす

叩いた音は声と形がまったく違う。**極端に短い（数十ms）／極端に大きい／低音寄り**。
低域比の計算はVAD計測モードに実装済みなので、判定を足すだけ。
2回叩き（コンコン）を条件にすれば、物がぶつかった誤検知も落とせる。

### 遠隔無音ベル

声を出さずに呼べることに、他にない価値がある（夜間・人前・声が出しづらいとき）。
離れた家族から呼ぶ使い方もでき、DOから機体へ落とす経路は既存のWebSocketがそのまま使える。

### 声で判定

肩乗りで口が近い点を使い、機体側で「装着者が喋ったか」を判定して、その分だけクラウドへ送る。
クラウドで文字にして呼びかけかを判断する。呼び名は設定画面から自由に変えられる
（アプリ側 yorisoi-care-app と同じ考え方）。

実測で確定したことは[付録C](#付録c-実測で分かったこと)。

### 目線（カメラ）

🔴 **「目線」は取れない。取れるのは顔の向きだけ（2026-08-14・ユーザーが PC 上で実験済み）。**
**視線そのものは全然取れず、取れても顔の方向だった。** この項目を「目線で確認」として
計画するのは、実測に反する。**以後は「顔の向きで確認」として扱う。**

視線を扱う技術には段階があり、この機体で届くのは 1 までである。

| 段階 | 何が分かるか | この機体で |
|---|---|---|
| 1 | **顔がこちらを向いているか** | ✅ **ここまで**（実験で取れたのはこれ） |
| 2 | 目が合っているか | ⚠ 目の領域が数十ピクセル要る |
| 3 | 視線の方向を角度で出す | ❌ 実験で取れなかった |
| 4 | 角膜反射と瞳孔から確定する | ❌ **原理的に無理。** IR照明・近距離・個人ごとの較正が要る据置き/眼鏡型の技術 |

⚠ **本当の壁は解像度ではなく角度である。** 肩の位置は顔の下から見上げるので、
まぶたと頬骨で目が隠れる。**画素を増やしても、下から見上げている限り改善しない。**

カメラを回し続けるのはウェアラブルでは電力的に厳しい。**音で起こして、その瞬間だけ見る**。
声が聞こえた瞬間に数百msだけカメラを見て、こちらを向いていれば反応する。
カメラは1日数分しか動かず、クラウドへ送る前に判断できる。

**買う前にやること**: ロボットを載せる位置にスマホを置き、(1)正面を向いたとき
(2)ロボットを見たとき の2枚を撮る。そもそも顔が写るか、2枚が明らかに違うかを見る。
ここで駄目ならカメラを買っても解決しない。
⭐ **切り離す前提（下）なら、この実験は「置く場所を決める実験」になる。**
肩の高さと胸元の2箇所で撮り比べれば、どこに置けば通るかが分かる。

#### カメラは無線で切り離す（2026-08-14・ユーザー提案）

**カメラを本体に配線せず、別ユニットにして無線で繋ぐ。** 高画質である必要はない。

| 効くところ | 中身 |
|---|---|
| **MCU の条件が緩む** | カメラは「逃がせないもの」の筆頭で、アプリ側 MCU を30本級・DVPペリフェラル必須に縛っていた**唯一の理由**だった。外に出すと要件は 11〜17本まで落ちる（[ARCHITECTURE.md](ARCHITECTURE.md)） |
| **置く場所を選べる** | 上の「角度」の問題が、解像度ではなく**配置**で解ける問題に変わる |
| **画像を送らなくてよい** | 欲しいのは「向いているか」の真偽だけ。**カメラ側で判定して結果だけ送れば帯域の問題は消える。** 画像が機体の外に出ないので、[仕様書](../仕様書.md)の「カメラ監視のプライバシーリスクを排除」ともまっすぐ合う |
| **ESP-IDF 移行を閉じ込められる** | 移行が要るとしてもカメラ側の1台だけで済み、本体のファームは触らない |

#### カメラは機体から少し離れた所に置く（2026-08-14・ユーザー）

**肩には置かない。** 上の角度の問題は、肩に置いている限り解像度では解けないため。

これで性質が3つ変わる。

| | |
|---|---|
| ✅ **充電するものは増えない** | 据え置きなら常時給電にできる。当初の懸念（高齢者に「今日はどちらを充電したか」を増やす）が消える |
| ⚠ **その部屋にいるときだけ効く機能になる** | 外出時は使えない。BLE の届く範囲は見通しで10m程度で、同じ部屋なら足りるが家中はカバーしない |
| 🔴 **受け取られ方が変わる** | **肩のカメラより、部屋に置かれたカメラのほうが「見張られている」と感じられやすい。** 画像を外に出さない作りであっても、置いた瞬間の印象は別物である。[仕様書](../仕様書.md)が「カメラ監視のプライバシーリスクを排除」を掲げている以上、**説明の仕方まで含めて設計に入る** |

障害: 肩のカメラは周りが身構える。
XIAO ESP32S3 の Sense 版が同じ形でカメラ付きだが、ESP-IDF 移行が要る可能性が高い。

### アクティブモード（軸B）

複数人の会話に自分から入る。アプリ側にすでに「AIの好奇心」「プロアクティブトーク」が
あるので、**何を喋るかの判断はそちらの資産を持ってこられる**。ロボット側で新しく要るのは
「聞き続ける」「誰が喋ったか」「いつ入るか」の3つ。

難しいのは判定ではなく**間の取り方**。何を喋るかより、いつ黙るか。
少しでも入りすぎた瞬間に鬱陶しくなる。先に決めておくこと:

- 明示的にONにするモードにする（常時聞く状態を既定にしない。同席者の同意の問題）
- 黙ることを既定にする（迷ったら入らない）
- 入った回数を数えて自制する

未検討: 話者分離をマイク1本でどこまでできるか。入るタイミングをどこで判断するか。

## 却下したもの

同じ議論を繰り返さないために残す。

| 案 | 却下の理由 |
|---|---|
| microWakeWord / WakeNet で語を学習 | 語を変えるたびに学習と書き込みが要る。呼び名を自由にできない |
| ReSpeaker `ch0-asr/ch1-mww` ファーム | ウェイクワードを検出しない。外部エンジン向けの音声を出すだけ。DFU版は48kHzで現構成と不一致 |
| Picovoice Porcupine | 対応が Arm Cortex-M4 のみ。ESP32-S3(Xtensa)では動かない |
| ブラウザの音声認識モデルを載せる | 実体は数百MBのネイティブ部品かクラウド。ESP32とは桁が2〜3つ違う |
| 音源方向（DOA）で判定 | 4マイクの上位機の機能。Lite(2マイク)では取り出せず、I2Sから来るのは処理済み音声 |
| 発話の長さで呼びかけを判定 | 実測で逆に出た（[付録C](#付録c-実測で分かったこと)） |
| 低域比（近接効果）で装着者を切り分け | 2026-09-21 の実測で分離しなかった。**そもそも要らない**（[付録D](#付録d-2026-09-21-の実測距離で分けられる)） |
| 加速度センサーで体の振動を拾う | **置いても使う**ので体に触れていない場面がある。AirPods 方式はこの機体では成立しない（2026-09-21・ユーザー指摘） |

## 付録A: 費用

クラウドで文字にする方式でも、費用は判断材料にならない。

- Cloudflare Workers AI `whisper-large-v3-turbo`: **音声1分 $0.00051**
- 無料枠: **1日10,000ニューロン ≒ 音声3.5時間ぶん**

装着者が喋った分だけ送るなら1日数分〜数十分。無料枠に収まる見込み。
会話を聞き続けるアクティブモードでも3.5時間/日までは無料。
判断がCloudflare内で完結するので、呼ばれたと分かるまでGoogleへは何も送らない。

## 付録B: 計測のやり方

`firmware/esp32/` を書き込み（`pio run -t upload`）、シリアルで操作する。
音声はどこにも送らない。

| 入力 | 内容 |
|---|---|
| `vad` | 計測の開始/終了。最初の2秒は静かにする（騒音床の測定） |
| `me` | 以降の声を【自分】/【周囲】で切り替える（正解ラベル） |
| `vadme` | 自分の声を4秒測ってゲートを自動設定 |
| `vadth <RMS>` | ゲートを直接指定（0で自動） |

`me` で自分と周囲を交互に切り替えながら数回ずつ喋る。1分ごとに判定が出る。

```
[VAD] 区間 0.56秒  音量RMS=2547 (床の15.6倍)  低域比=0.71  [自分]  → 送る
[VAD] 正解ラベル 自分8回(最小RMS=2100) / 周囲6回(最大RMS=1500) → 音量で分離できています
[VAD] 低域比の平均 自分=0.71 / 周囲=0.48 → 近接効果が出ています
```

計測中はBOOTボタンもラベル用になり、会話・設定モードは動かない。

## 付録C: 実測で分かったこと

2026-07-26、肩乗り・隣に家族がいる状態での実測。

- **絶対音量は当てにならない。倍率で見る。** 騒音床が38〜469と12倍動いた
  （ReSpeaker側の自動音量調整）。倍率は安定していて、装着者が床の15〜58倍、
  隣にいる家族が4〜10倍
- **長さでは分けられない。** 装着者の5秒の発話と家族の0.2秒の相槌が、
  長さの判定では逆に出る
- **騒音床は追従させる。** 1回だけ測る実装では、部屋が騒がしくなった時点で
  「発話中」のまま固まり2分間無反応になった
- **低域比は未検証。** XMOSのノイズ抑制で低域が削られていると使えない

## 付録D: 2026-09-21 の実測（距離で分けられる）

同じ人が同じ調子で、距離だけ変えて喋った。エアコン・PC のファン・換気扇は鳴ったまま。

| 距離 | 何にあたるか | 区間 | RMS | 低域比 | ゲート |
|---|---|---|---|---|---|
| 40cm | 肩に載せたときの本人 | 1.93〜2.04秒 ×3 | 10455〜16859 | 0.46〜0.59 | 全部 送る |
| **1m** | **置いて使うときの本人** | 0.80〜2.32秒 ×4 | 1880〜2632 | 0.25〜0.40 | **4/4 送る** |
| **3m** | **隣の人** | 0.11〜1.00秒 ×20 | 405〜2594 | 0.10〜1.00 | **19/20 落とす** |

**結論: 低域比は使えないが、要らない。** 距離が 1m と 3m なら、検出線（騒音床×3）と
ゲートだけで分かれる。低域比は 1m が 0.25〜0.40、3m が 0.10〜1.00 で重なる。

- 🔴 **誤って通ったのは 20 区間中 1 つ**（0.36秒・RMS 2594・低域比1.00）。**最短区間 0.5 秒の
  条件を足せば落ちる**（1m 側の最短は 0.80秒なので、本人は削られない）
- ⚠ **低域比は 1 秒未満の区間では当てにならない。** 0.11〜0.36秒の区間で 0.10〜1.00 まで散る。
  使う場面があっても 1 秒以上に限ること
- ⚠ **騒音床は 2 秒の初回測定では実勢に届かない。** 1 回目は床 RMS=83 と出たが実勢は 150〜700 で、
  検出線 207 を下回れず「発話中」のまま 10 秒の上限で切られ続けた（区間が成立しない）。
  ReSpeaker の自動音量調整が時間差で動くため。測り直すと床 209 で乗った
- ⚠ **距離で落ちる量は逆二乗より急。** 40cm → 1m（距離2.5倍）で RMS が 12〜25分の1
  （逆二乗なら 6分の1）。ReSpeaker が遠い音を落としているぶん、狙いには有利に働く
- 📄 参考（距離を測っていないので判定には使わない）: PC スピーカーのアニメは RMS 712〜11297。
  大きい場面は 40cm の本人（最小 10455）と音量で重なる

## 付録E: 2026-09-21 の実装（呼びかけで会話が始まるところまで）

機体が VAD で切った区間だけを `POST /wake` へ送り、バックエンドで
`whisper-large-v3-turbo` にかけて呼び名の有無を返す。入っていれば会話を始める。

| 測ったもの | 値 |
|---|---|
| 呼びかけの判定（送信〜返事） | **2.7〜6.6秒** |
| サーバー接続（setupComplete まで） | 1.6〜1.8秒 |
| 呼んでから会話が始まるまで | **4.3〜8.4秒** |
| 送るぶんの費用の目安 | 月 40〜425円（機体の表示。無料枠 3.5時間/日の内） |

🔴 **待たせる間に黙っていてはいけない。** 判定に数秒かかるので、何も返さないと
届いていないと思って呼び直される。実機で4回呼ばれ、その全部が控えから送られて
Gemini が別々の発話として扱い、応答が割り込みで捨てられ続けた
（ユーザー「応答がないからだよ。そりゃ呼ぶわ」）。**顔（目）と音で即座に返す。**
音は木を2回叩いた音（`firmware/esp32/tools/gen_wake_chime.py`）。
⚠ 顔だけでは足りない。機体を見ていない場面がある。口は音に反応して出るだけなので、
黙っている間に変わるのは目（16→19px）だけである。

### 数字で決めたこと

| 決めたもの | 値 | 根拠 |
|---|---|---|
| 最短の区間 | **0.3秒** | 呼び名だけを言うと 0.36秒 にしかならない。0.5秒 にしたら呼びかけ自体が落ちた |
| 控えに遡る長さ | **1.5秒** | 「カタノリ、〜」と間が空くと呼び名が手前の区間に落ちる。呼び名 0.7秒＋区切りの無音 0.5秒 |
| 控えの無音を詰める | **0.2秒 まで** | 一括で送ると Gemini が無音の長さを実時間として扱わず、0.44秒 の間で発話を切る |
| 1回に送る長さ | **最大4秒** | 呼び名は文頭近くに来る。送った量が費用になる |
| 会話後に見張るまで | **1.5秒** | 鳴り終わった直後はロボットの声が残る |

### 踏んだ穴（同じ道を通らないために）

- 🔴 **`isRecording()` を「会話中か」の代理に使ってはいけない。** マイクの用途が
  3つ（見張り・計測・会話）に増えたので、判定する場所ごとに条件を足して回る形になり、
  同じ原因のバグが4件出た（見張り開始→即「60秒無音」で会話終了→再開の無限ループ／
  会話ボタンが「終了」に倒れる／計測モードに入れない／呼ばれた直後に閉じる）。
  **マイクの用途を1つの状態として持つ**リファクタリングが要る（未了）
- **騒音床は「静かなとき」だけ追従させると固まる。** 起動直後の2秒で測った値が
  実勢とずれると（実機で床 2〜5 に対して環境音 100〜300）、検出線を割る瞬間が
  来ないので追従が一度も掛からない。直近5秒の底を見て、発話中でも寄せ直す
- **打ち切り時の測り直しは `vadCloseSegment()` の前に値を控える。** あの関数が
  `vadSegMinRms` を 0 に戻すので、後から読むと必ず 0 になり床が据え置かれていた
- **控えを流し込むまでライブ送信を始めない。** 繋がった瞬間から送ると、直後の
  `drainToNetLink()` が同じところをもう一度送って二重になる
