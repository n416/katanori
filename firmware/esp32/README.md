`firmware/core` / `firmware/hal` のコアロジックを実機で動かすための PlatformIO プロジェクトです。
コアはシミュレーターと**同一のソースを共有**しています（コピーを作らないこと）。

## 構成

```
firmware/
├── core/          ← シミュレーターと共有（Arduino依存禁止・純C++14）
├── hal/           ← IHal インターフェース
└── esp32/         ← このPlatformIOプロジェクト
    ├── platformio.ini
    └── src/main.cpp   ← 唯一の実機依存コード（Esp32Hal + setup/loop）
```

`platformio.ini` の `build_src_filter` で `../../core/*.cpp` をビルド対象に加えているため、
コア側を修正すると実機ビルドにもそのまま反映されます。

## 配線（実機で確認済み）

XIAO ESP32S3 を ReSpeaker Lite に直挿しした構成。OLED は ReSpeaker Lite が使っている
I2Cバス（D4/D5）に相乗りさせる。**このバスにはプルアップが既に載っている**ため追加不要。

| OLEDのピン | XIAO | GPIO |
|---|---|---|
| `VCC` | 3V3（右側ヘッダ上から3本目） | — |
| `GND` | GND（右側ヘッダ上から2本目） | — |
| `SCL` | D5（左側ヘッダ上から6本目） | 6 |
| `SDA` | D4（左側ヘッダ上から5本目） | 5 |

```
          ┌──[USB-C]──┐
   D0 ────┤           ├──── 5V
   D1 ────┤           ├──── GND
   D2 ────┤           ├──── 3V3
   D3 ────┤           ├──── D10
   D4 ────┤           ├──── D9      D4 = SDA (GPIO5)
   D5 ────┤           ├──── D8      D5 = SCL (GPIO6)
   D6 ────┤           ├──── D7
          └───────────┘
```

注意点:

- **VCC は 5V ではなく 3V3 に繋ぐこと。** 5Vを与えるとモジュール側のプルアップが
  I2Cラインを5Vへ引き上げ、ESP32の入力定格を超える。
- 使用しているOLEDモジュールのシルクは **`VCC GND SCL SDA`** の順で、一般的な
  `VCC GND SDA SCL` とは SCL/SDA が逆。並び順の記憶で挿すと入れ替わる。
- 起動時にOLEDが繋がっていないと初期化コマンド列がパネルに届かない。配線を直した後は
  リセットするか、シリアルで `r` を打って再初期化すること。

I2Cスキャンでは ReSpeaker Lite 側のデバイスが `0x18` に、OLEDが `0x3C` に見える。
両方出れば配線は正常。

### Usrボタン（はんだブリッジ必須・実機で確認済み 2026-07-27）

ReSpeaker Lite 裏の **Usrボタンで会話を開始できる**（XIAOのBOOTボタンは小さすぎて実用にならないため）。
ただし Usrボタンは XMOS XU316 側に繋がっていて、**そのままでは ESP32 から見えない**。

- ReSpeaker Lite の XIAO が載っている面、左下に **`Mute D3 D2 Usr`** と印字された穴の列がある
- **`Usr` と `D2` の導通が必要**（Seeed公式の想定でははんだブリッジ。
  [Usr Button Usage](https://wiki.seeedstudio.com/respeaker_button/)）
- これで Usrボタンが **D2 = GPIO3**（`KATANORI_USR_BUTTON`）に押下=LOWで入る

> 🔧 **記録訂正（2026-08-02・ユーザー確認）**: 以前ここに「はんだブリッジしてある」と
> 書かれていたが、**実機にはんだ付けは一切していない**。Usr-D2は**ジャンパー
> （ブレッドボード用ピン）を穴に通してぶら下げているだけ**（固定なし・ブラブラの
> 状態でスルーホールのメッキに触れて導通している）。取り外し自由で基板は無改造。
> 当時ユーザーは画像付きで「ジャンパーで繋いでいるだけ」と報告していたのに、
> AIが勧めていた「はんだブリッジ」が実行されたものとして記録された（誤変換の経緯）。

**Usr-D2 が導通していない個体では Usrボタンは一切反応しない。** 新しいボードを組むときは導通方法を決めてから。

- ファーム側は BOOTボタンと Usrボタンを同じ扱いで読む（`anyButtonPressed()`）。
  短押し=会話開始/終了、3秒長押し=Wi-Fi設定モード
- **Muteボタンはブリッジしない。** XMOS側でマイクミュートとして実際に機能しているため
- GPIO3 はストラッピングピン。INPUT_PULLUPで読むだけなら無害だが、**リセットの瞬間に
  押しっぱなしにしない**こと

### 音量つまみ（AS5600・2026-08-02 ファーム移行済み）

主経路は **AS5600（I2C 0x36）の `RAW ANGLE`**。ゼロ点（NVS `knob/zero`）からの
相対角度を 0-100% へ写す。設計と実測は [docs/KNOB-ENCODER.md](../../docs/KNOB-ENCODER.md)。

- ビルドフラグ: `KATANORI_KNOB_SPAN_DEG`（既定270・ゼロ点からこの角度で100%）/
  `KATANORI_KNOB_OFF_DEG`（既定5・この角度未満でOFF、+3度のヒステリシス）/
  `KATANORI_KNOB_DIR_INVERT`（回して%が逆に動く組み付け用）
- コマンド: `knobzero`（今の位置をゼロ点として保存）/ `knobsrc`（読み元の再判定）/
  `knob`（角度・%・ゲインに加えて磁石の MD/ML/MH・AGC・MAGNITUDE）
- **起動時に 0x36 が応答しなければ下の可変抵抗(ADC)経路へ自動フォールバック**する。
  動作中に5回連続で読めなくなったときも同様（机の上で配線を差し替えて切り替えられる）
- 治具での実測（2026-08-02）: ゼロ点保存→90度ごとに 0/28/64/97% の単調増加、
  12時戻りでOFF復帰、ゼロ点を数度行き過ぎても範囲外折返しで0%に倒れる。
  つまみを外したままだとADCフォールバックのピン浮きでOFF誤認するので `knobdis` を使う

### 音量つまみ・旧経路（スイッチ付き可変抵抗・2026-07-29 配線）

RV121SF-20-02J-B10K（10kΩ Bカーブ・SPST連動スイッチ付き）。

> ⚠ **これはフォールバック経路の記録であって、これから作る設計ではない。**
> **2026-08-02、ファームはAS5600（非接触）へ移行済み**（上の節）。
> `kKnobCurve`・ADC経路・`knobSwitchRawOn()` は「0x36が応答しないとき」だけ動く。
> **可変抵抗まわりを新規に設計・買い足ししないこと。**

| つまみの足 | 接続先 | 備考 |
|---|---|---|
| 上の足（OFF位置でワイパーが導通する側） | **GND** | 左に回し切り=0Vで最低音量になる向き |
| 中央の足（ワイパー） | **D0 = GPIO1** | ADCで読む。**3V3系。5Vは絶対に入れない** |
| 下の足（最大位置でワイパーが導通する側） | **3V3** | |
| 連動スイッチ2本 | **D1 = GPIO2** と **GND** | 2本に向きは無い。INPUT_PULLUPで読む |

- ⚠ **XIAOのシルク `D0`/`D1` は GPIO0/GPIO1 ではない**（D0=GPIO1、D1=GPIO2）。
  ここを読み違えるとワイパーとスイッチが入れ替わり、「音量が0か最大しかない・
  回転の途中で疑似電源OFFに入る」という症状になる（2026-07-29 に実際に踏んで、
  コネクタで入れ替えて復旧した）
- **現在の機体は外側2本が上表と逆**（OFF位置側=3V3）のまま実装されている
- **ADC→位置(%)の換算は実測テーブル**（main.cpp の `kKnobCurve`）。この個体の
  抵抗カーブはB（直線）と称して実際は「3時で22%・4時→5時に全変化の6割」という
  極端な偏りがあり、線形換算では使いものにならなかった（2026-07-29 実測）。
  向き（外側2本の付け方）の吸収もこの表が担う（旧 `KATANORI_VOL_INVERT` は廃止）。
  **つまみを交換・再半田したら各位置で `knob` を読んでテーブルを取り直すこと**
- ~~組立中に3V3-GNDの短絡事故があった~~ **記録訂正（2026-08-02・ユーザー確認）:
  3V3-GNDの短絡は実際には起きていない。** 以前のセッションの誤診断が事実として
  書かれていた。故障原因の候補からも外すこと
- 待機中にログへ「ミュートしました」が出続けるのは**仕様**（出力ゲートは
  鳴らすものがある間だけ開く）。故障判定は「会話の応答中にも無音か」で行う
- **スイッチは電源線に入れない**（定格DC12V 0.5A。GPIOで読めば数μAで定格が無関係）
- 論理は **ON位置=接点が閉じる=LOW**（アクティブLOW。Usrボタンと同じ作法）。
  「OFF位置なのにHIGH」は故障ではなく仕様。逆に振る舞う個体は
  ビルドフラグ `-DKATANORI_KNOB_SW_INVERT=1` で反転できる
- OFF位置の挙動: 会話を終了し、出力ゲートを閉じたままにする（手動 `unmute` より優先）。
  ボタンを押しても会話を開始しない
- 確認コマンド: `knob`（ADC生値・位置%・ゲイン・スイッチ状態、および下の疑似電源OFFの
  進み具合を表示）。つまみを回して 0〜100% がなめらかに動けば配線は正しい

### 疑似電源OFF（つまみOFF位置・`pumpPowerDown()`）

電源基板が無いので**本当には切れない**（USB給電でも電池でもXMOSごと生きている）。
ESP32側だけを畳んで「切れたように見せる」のがこの処理。

| OFF位置になってから | すること |
|---|---|
| 即時 | 会話終了・出力ゲートを閉じる・顔とマイクを止める |
| 2秒後 | OLED消灯（`setPowerSave(1)`。バッファは残るので戻せば同じ絵が出る） |
| 5秒後 | `wsDisconnect()` → `wifiDisconnect()` → ユーザーLED消灯 |

- **一気に落とさない理由**: 回し切る途中で一瞬OFFを通ることがあり、また「切ったつもりが
  違った」とすぐ戻すこともある。落とし切る前にONへ戻せば、その段階は実行されない＝
  何も起きなかったことになる。落とした後に戻した場合は**落とした分だけ**戻す
  （画面を点け、Wi-Fi再試行の待ち時間を捨てて即座に自動接続へ行く）
- 通信を落とすまでの5秒間は WebSocket を生かしたまま `netLink.loop()` を回す。
  ここで戻れば繋ぎ直しが要らない（再接続はWi-Fiだけで十数秒かかる）
- ユーザーLEDは「通信中」の表示なので、**切断が終わってから**消す
- 昇圧ICのEN制御は、この5秒後の処理の**最後**に足す。そうすると
  ミュート→切断→電源断の順序が構造的に守られる（[docs/POWER.md](../../docs/POWER.md)）
- Wi-Fi設定モード中は動かない（画面もAPも要るため）。設定モードを抜けた時点で効き始める
- **`WiFi.mode(WIFI_OFF)` までは落としていない**（`wifiDisconnect()` 止まり、
  `main.cpp` の `powerWifiOff`）。消費電流は WIFI_OFF のほうが小さいので、
  本当は落としたい。実測してから決めること。

  > **この判断を2度間違えている。** 「WIFI_OFF にするとI2Sが巻き添えで止まる」
  > (2026-07-29) → 「I2Sではなくコーデックの設定が飛ぶ」(2026-07-30) → **どちらも誤り**。
  > 根拠にした試験はどちらも「つまみを回す」操作を含んでいて、そちらが犯人だった。
  > `wifistop` で WIFI_OFF を15秒保持しても、コーデックは生きたままになる。
  > **一度に1つしか変えないこと。**

> ⚠ **つまみを回すとコーデックが死ぬ問題は未解決です（2026-07-30 再発）。**
> 半田をやり直したら止まったように見えましたが、再発しました。死ぬのは**回している
> 最中**で、スイッチが開く4.9秒前 — つまりファームの経路は無関係です。
> 経緯と実測は [docs/KNOB-TROUBLE.md](../../docs/KNOB-TROUBLE.md)。
> **回避策**: スイッチの2本を外せば音量つまみとしては使える（OFF機能だけ失う）。
> **復旧**: USB抜き差し（ESP32の再起動では戻りません）。

### 切り分け用のシリアルコマンド

| コマンド | 何をするか |
|---|---|
| `creg` | コーデックの主要レジスタをダンプ。正常時は `0x3F=0xD4` / `P1 0x09=0x3C` |
| `knobdis` | つまみの読み取りを止める/再開。**配線を外して切り分けるときは必ずこれ**（外すとピンが浮いてOFF位置と誤認し、ソフト側の理由で無音になる）。⚠ **疑似電源OFF中に打つと復帰処理が走る**（画面点灯・Wi-Fi再接続・**コーデックのミュート解除・起動ボイス再生**）。ゲインが0でなければ音が出るので、**イヤホンを着けたまま打たないこと** |
| `low <d>` | 指定したDピンを300ms LOWにする。「このピンをGNDに繋ぐと何が起きるか」を手を使わずに再現する |
| `pwr` | 疑似電源OFFの有効/無効。前節の処理を丸ごと切れる |
| `reboot` | ESP32だけ再起動。**この機体はRSTボタンが押せない位置にある**ため。USB給電は切れないので「ESP32だけ」の切り分けに使える |
| `mag` | **AS5600(0x36)の磁石の状態と角度**を1回表示（読み出しのみ。OTPには一切書かない）。`STATUS` の MD/ML/MH・`AGC`・`MAGNITUDE`・`RAW ANGLE`・`ANGLE` を出す。つまみの非接触化の組み付け確認用（[docs/KNOB-ENCODER.md](../../docs/KNOB-ENCODER.md)）。**電源断用リードスイッチの磁石が角度を狂わせていないか**もここで見る（[docs/POWER.md](../../docs/POWER.md)） |

`pumpCodecWatch()` が200msごとにコーデックを見張っていて、出力が死んだ瞬間と復帰した
瞬間をログに出す。**これが無いと、音を鳴らすまで気づけない。**

コマンドは `pio device monitor` に手で打ってもよいが、決まった手順を流して結果を
持ち帰るなら [tools/ser.py](tools/ser.py) が楽（行頭に経過秒が付く）。

```bash
python tools/ser.py 3 knobdis creg
```

## セットアップ

PlatformIO Core をインストールします（VS Code拡張版でも可）。

```bash
pip install -U platformio
```

`pio` にパスが通らない環境では `python -m platformio ...` でも同じことができます
（`pip install --user` の場合はこちらが確実）。初回の `pio run` は
ツールチェーンを取りに行くので数分かかります。

**USBドライバは要りません。** XIAO ESP32S3 はネイティブUSB（USB-Serial-JTAG）で、
Windows 11 なら挿すだけで「USB シリアル デバイス (COMn)」として見えます。
CH340/CP210x のようなドライバを入れる必要はありません。ポート番号はPCごとに
変わるので、機械を替えたら確認してください。

```bash
pio device list
```

## ビルドと書き込み

XIAO ESP32S3 を USB-C で PC に接続してから、このディレクトリで実行します。

```bash
pio run -e xiao_esp32s3 -t upload
```

書き込み後、シリアルモニタを開きます。

```bash
pio device monitor -e xiao_esp32s3
```

### 書き込みできない場合（ブートローダーモード）

XIAO ESP32S3 の **BOOT ボタンを押しながら RESET**（または BOOT を押しながらUSB接続）すると
ダウンロードモードに入ります。COMポートが見えない場合はこれを試してください。

## 動作確認（Stage 1 の完了条件）

1. シリアルに `[I2C] device found at 0x3C` が出る → **配線OK**
2. OLED に目が表示され、数秒おきにまばたきする → **描画OK**
3. シリアルモニタから `1` `2` `3` `4` を送ると顔が変化する → **状態機械OK**

| 入力 | イベント | 遷移 |
|---|---|---|
| `1` / BOOTボタン | `WAKE_WORD` | IDLE → LISTEN |
| `2` | `SPEECH_END` | LISTEN → THINK |
| `3` | `RESPONSE_READY` | THINK → SPEAK |
| `4` | `SPEECH_DONE` | SPEAK → IDLE |

シミュレーターのキー操作と同じ割り当てです。
`wrapper.py` が送る `CMD:SPEAK_START` / `CMD:SPEAK_END` も受理します。

### 診断コマンド

ネイティブUSB CDC のため、`upload` 直後のブートログはモニタを開く前に流れてしまいます。
以下のコマンドで後からいつでも同じ情報を取れます。

| 入力 | 内容 |
|---|---|
| `s` | I2Cバスを再スキャン（配線確認） |
| `a` | D0〜D10 の全ピン組み合わせを I2C として叩き、OLED(0x3C/0x3D)がどのピンに繋がっているかを探索 |
| `vN` | D`N` ピンの電圧を測る（簡易電圧計）。例 `v0` |
| `gN` | D`N` ピンが GND に導通しているか見る（簡易導通チェッカー）。例 `g1` |
| `t` | OLED自己診断パターンを5秒表示（`DisplayBuffer` を通さず U8g2 直描画） |
| `bn` | 接続状況の表示（顔の代わりに出る2行）を4種類、3秒ずつ出す。文字の大きさの確認用 |
| `i` | チップ・メモリ・I2Cピン設定を再表示 |
| `?` | ヘルプ |

`t` は**画面が出ない原因を二分する**ためのものです。

- `t` で枠と `KATANORI SELFTEST` が見える → 配線とOLED初期化はOK。原因は `DisplayBuffer` → U8g2 の転送側
- `t` でも真っ暗 → 配線・I2Cアドレス・給電のいずれかの問題

同じ理由で、起動直後にも自動でこのパターンを5秒表示します。

### テスター代わりの使い方

`vN` / `gN` はテスターが手元にないときに ESP32 自身を簡易計測器として使うためのものです。
調べたい点から D`N` ピンへジャンパーを1本渡して実行します。

- `v` は ADC で電圧を読みます。**入力は 3.3V まで。5V の点に繋ぐとピンが壊れます**
- `g` は内部プルアップを有効にして読むだけ。LOW なら GND に導通しています
- ADC非対応のため `v` は D6 / D7 では使えません（D0〜D5、D8〜D10 を使うこと）

## Stage 2: ネットワーク

Wi-Fi資格情報は **NVS(Preferences) に保存**します。ソースにも `platformio.ini` にも
書かないため、gitに漏れません。書き込み直しても消えません。

| 入力 | 内容 |
|---|---|
| `ssid <名前>` | SSID を保存 |
| `pass <パスワード>` | パスワードを保存（ログには出しません） |
| `forget` | 保存した設定を消去 |
| `wifi` | Wi-Fi へ接続（普段は自動。手動で試したいとき用） |
| `wifioff` | Wi-Fi を切断 |
| `c` | Durable Object へ WebSocket 接続（普段はボタンを押した時に自動で張る） |
| `d` | WebSocket を切断 |
| `n` | ネットワーク状態を表示 |

### 完了条件（実機で確認済み）

```
[NET] 接続しました  IP=192.168.0.18  RSSI=-44dBm  (1.0秒)
[WS] 接続しました (0.9秒)
[WS] ★ setupComplete 受信 — Geminiまで疎通しました
[WS] BIN 26bytes: {"setupComplete": {}}
```

接続開始からGeminiの応答まで実測 **1.06秒**。WebSocket 接続中は内蔵LEDが点灯します
（仕様書の「通信中のステータス表示」）。

空きヒープの実測値: Wi-Fi接続前 292KB → TLS+WebSocket接続後 **248KB**（TLSで約44KB消費）。

### アンテナは必須

XIAO ESP32S3 は外付けアンテナ前提の設計です。**U.FL コネクタにアンテナを挿していないと
実質的に通信できません。** 実測で 40dB（電力比1万倍）の差が出ました。

| | アンテナなし | アンテナあり |
|---|---|---|
| 自宅APのRSSI | -86dBm | **-46dBm** |
| 検出できたAP数 | 2件 | **15件** |
| Wi-Fi接続 | 失敗 (WL_DISCONNECTED) | 成功 (0.8秒) |

スキャン（ビーコンを聞くだけ）は通っても接続（双方向のやりとり）は落ちるため、
「SSIDは見えるのに繋がらない」という紛らわしい症状になります。

### 実機で判明したこと: Geminiの応答はバイナリフレーム

Gemini Live API は応答を **WebSocket のバイナリフレーム**で返してきます（中身はJSONテキスト）。
`wrapper.py` では Python の websockets ライブラリが bytes と str を透過的に扱うため
表面化しませんでしたが、実機では TEXT と BIN の両方を同じように読む必要があります。
**Stage 3 の音声受信でも同じ扱いになります。**

### 起動後の自動接続

渡した相手はUSBもシリアルコンソールも持たない。**電源を入れるだけで会話できる状態まで
自力で行き着く**必要があるため、`main.cpp` の `pumpAutoConnect()` が以下を回します。

1. 保存済み設定があれば起動後すぐWi-Fiへ接続する（`wifi` を打つ必要はない）
2. 失敗したら 5秒 → 10秒 → 15秒…（上限30秒）と間隔を広げて試し続ける。
   ロボットのほうがルーターより先に起きる場合に備えるため
3. **一度も繋がらないまま3回失敗したら設定モードへ落ちる**。SSID変更や
   パスワード間違いを利用者が自分で直せるようにする

3の条件が「一度も繋がっていない場合のみ」なのは意図的です。会話中にルーターが
再起動しただけで設定モードへ入って会話が終わるのは、利用者から見て理不尽なため。
一度繋がった後の切断は再試行のみを続けます。

#### 繋がっていないことを利用者に伝える（2026-07-29）

引っ越して保存済みSSIDが消えた機体が、**顔だけを出したまま約1分間黙って**
再試行を続けました。顔は繋がっていてもいなくても同じように動くので、
利用者からは正常に見えてしまいます。3つ直してあります。

- **画面**: 繋がっていない間は**顔をやめて**、16pxの日本語を2行で出す
  （`netMsg1/netMsg2` / `Esp32Hal::flushDisplay`）。繋がれば顔に戻ります。

  | 状態 | 表示 |
  |---|---|
  | 接続中 | WiFiに / つないでいます |
  | SSIDが無い | WiFiが / みつかりません |
  | それ以外の失敗 | WiFiに / つながりません |

  最初は**顔の下に10pxの帯を重ねる**設計にしましたが、実機で読めませんでした
  （128pxに9文字入れると1文字10pxしか使えず「つ」が潰れる）。文字を大きくすると
  顔と同居できないので、**伝えるほうを優先して画面ごと明け渡しています。**

  フォントは `u8g2_font_b16_t_japanese1`（+46KB）。**かなとASCIIだけ使うこと。**
  japanese1 に無い漢字は幅0で消えます。1行は全角8文字（128px）が上限で、
  超えるとシリアルに `[UI] !! "..." は NNNpx` が出ます。

  文字の大きさは繋がっている機体では確かめられないので、**シリアル `bn`** で
  4種類を3秒ずつ画面に出せるようにしてあります。文言を変えたら必ずこれで見ること。
- **打ち切り**: 切断理由が結論の出ているもの（201 NO_AP_FOUND / 202・15 認証失敗）
  なら、タイムアウトを待たず接続試行を打ち切る。**12秒 → 実測2.5秒**。
- **顔を止めない**: `wifiConnect()` に待ち中のフックを渡し、接続待ちのあいだも
  描画を回す。渡さないと main loop ごと止まって顔が固まり、故障に見える。

結果、SSIDが消えた機体がQRを出すまで **約58秒 → 約23秒**（うち6.5秒は設定モード
起動時のスキャン。ポータルのSSID一覧を作るためのもので、ここは削っていない）。

**スキャンで「SSIDが在るか」を判定してはいけません。** 最初はそう実装しましたが、
名前を隠したAP（ステルス）が近くに1つでもあると「一覧に無い＝存在しない」と
言えなくなり、実機の環境がまさにそれで判定が成立しませんでした。加えて既定の
スキャンは13チャンネルで約6秒かかり、繋がる機体まで毎回遅くなります。
**接続を試した結果の理由コードのほうが速く、確かです。**

WebSocket は**ボタンを押した時に張ります**。DO はクライアント接続と同時に Gemini へ
繋ぎにいくため、常時接続や自動再接続は Gemini のセッションを浪費します
（`wrapper.py` と同じ「会話するときだけ繋ぐ」設計）。押した時点で未接続なら、
接続してから録音を始めます（`pendingTurn`）。

待つのは **`setupComplete` まで**（`netLink.wsReady()`）。WebSocketが繋がった時点では
Gemini側のsetupが終わっておらず、送った音声は捨てられます。最初のひと言が消える
という分かりにくい不具合になるため、ここを`wsConnected()`で済ませてはいけません。

### 焼き込み音声（起動アナウンス）

`src/VoiceClips.h`（自動生成・コミット対象）に 16kHz PCM を直接持っています。
サーバーに繋がる**前**や繋がらないときに鳴らす音なので、DO側のつなぎ言葉とは
別に、ファームのフラッシュに置く必要があります。

| クリップ | 鳴るとき |
|---|---|
| 「カタノリ、起動しました！」 | Wi-Fiに繋がって会話できる状態になった（電源1回につき1度だけ） |
| 「ワイファイの設定をしてください」 | 設定モードに入った（未設定・繋がらない・ボタン長押し） |

作り直しは backend 側のツールから行います（TTSのAPIキーがそちらにあるため）。

```bash
cd katanori-backend
node tools/gen-voice-clips.mjs   # VoiceClips.h を作り直す
node tools/preview-clips.mjs     # 焼く前にWAVで聴く
```

16kHzで持つ理由: 実機のI2Sは16kHz固定なので、24kHzのまま置くとマイコン側で
リサンプルが必要になり、そのまま流せば低く遅い声になります。フラッシュ消費は
16kHz 16bit モノラルで **1秒あたり32KB**（現在2クリップで108KB）。

再生後は必ず出力をミュートへ戻します（`pumpVoiceClip()`）。開けっ放しにすると
次のリセット時にROMブートログが轟音になります。キューが空になってから
250ms待ってから閉じるのは、I2Sドライバ内に残った送信待ちで語尾が切れるのを
防ぐためです。

### VAD計測モード（ウェイクワード方式の検証用・作業中）

`vad` で開始。音声はどこにも送らず、有声区間の回数・長さ・音量だけを数えます。

| 入力 | 内容 |
|---|---|
| `vad` | 計測の開始/終了 |
| `me` | 以降の声を【自分】/【周囲】で切り替える（正解ラベル） |
| `vadme` | 自分の声を4秒測ってゲートを自動設定 |
| `vadth <RMS>` | ゲートを直接指定（0で自動） |

計測中はBOOTボタンもラベル用（押しているあいだ【自分】）になり、会話・設定モードは動きません。

**検証している方式**: 決まったウェイクワードを覚えさせるのではなく、肩乗りで
「装着者が喋ったか」を音量で判定し、送った音声をクラウドで文字にして
「自分への呼びかけか」を判断する。呼び名を自由に変えられるのが利点
（アプリ側 yorisoi-care-app と同じ考え方）。費用は音声1分 $0.00051
（Cloudflare Workers AI whisper-large-v3-turbo、無料枠は1日1万ニューロン
＝約3.5時間ぶん）なので、実用上ほぼ無料。

**実測で分かったこと（2026-07-26）**

- **絶対音量は当てにならない。倍率で見ること。** 騒音床が 38〜469 と12倍も動いた
  （ReSpeaker側の自動音量調整）。一方で倍率は安定していて、
  装着者の声が床の15〜58倍、隣にいる家族の声が4〜10倍。
- **長さでは分けられない。** 装着者の5秒の発話と家族の0.2秒の相槌が、
  長さの判定では逆に出る。「呼びかけは短い」という仮定は捨てた。
- **騒音床は追従させないと固まる。** 起動時に1回測るだけの実装では、部屋が少し
  騒がしくなった時点で「発話中」のまま2分間無反応になった。静かなあいだ少しずつ
  更新し、10秒を超えた区間は打ち切って測り直す。
- **方向検知(DOA)はこの機体では使えない。** 4マイクの上位機(XVF3800)の機能で、
  ReSpeaker Lite(2マイク)には公式の記載がない。XMOSの制御ポート(0x42)も
  この機体のI2Cスキャンには出ず、用意されているのはDFUと設定用のみ。
  I2Sから来るのは処理済みの音声で、生のマイク2本ではないため自前計算もできない。
- **代わりに低域比（近接効果）を試している。** 口が近いほど低域が持ち上がる。
  距離で決まる物理現象なので「遠くの大声」に騙されない。XMOSのノイズ抑制で
  低域が削られていると使えないので、実測で判断する。**ここが未検証。**

### 設計上の注意

- ESP32 は **2.4GHz帯のみ**です。5GHz専用のSSIDには接続できません。

### TLS証明書の検証

`beginSslWithCA()` でルート証明書を検証しています（`src/RootCa.h`）。
検証あり/なしで接続時間は 0.85秒 → 1.7秒。

2026-07-26 時点の実チェーンから抽出した2つを信頼アンカーにしています。

```
leaf : tobira-sys.workers.dev
  <- Google Trust Services WE1   (中間)
  <- GTS Root R4                 ← 埋め込み
  <- GlobalSign Root CA          ← 埋め込み
```

PEMは連結して渡せるので、クロス署名が外れても片方で検証が成立します。

**ピン留めの宿命**: 接続先が発行元CAを変更するとこの機器は繋がらなくなります。しかも
「TLS検証に失敗した」とは表に出ず、ただ繋がらないだけになります。そのため
**一度も接続できないまま切断された場合はログでCA更新の可能性を示唆**します。

更新手順は `src/RootCa.h` のコメント参照。緊急避難は `-DKATANORI_TLS_INSECURE=1`
（常用しないこと）。

**限界**: `arduino-esp32 2.0.17` は `CONFIG_MBEDTLS_HAVE_TIME_DATE` が無効なため、
**証明書の有効期限は検証されません**。中間者攻撃は防げますが、期限切れ・失効した証明書を
弾く効果はありません。変えるにはフレームワークの再ビルドが必要です。
副作用として、SNTPによる時刻同期なしで検証が通ります。

## Stage 3: 音声

DO の PCMモード（`?pcm=16000`）に繋ぐため、ESP32 側は base64 も JSON 組み立ても
リサンプルも行いません。**生PCMを読んで送る / 受け取って書く**だけです。

### ReSpeaker Lite との I2S 結線（実機で確定）

XIAO は ReSpeaker Lite に直挿しなので配線作業は不要です。ピンは Seeed公式の I2S サンプル
（`I2S.setPins(8, 7, 43, 44)`）と同じですが、**クロックの向きとスロット幅は公式サンプルと
違いました**。実機での総当たり（`scan2`）で確定させた値がこれです。

| 項目 | 当初の実装 | 正解 |
|---|---|---|
| クロック | ESP32がマスタ | **ESP32はスレーブ**（XMOSがマスタ） |
| スロット幅 | 16bit | **32bit**（データは上位16bit） |
| フォーマット | 標準I2S | 標準I2S（これは合っていた） |

総当たりの実測値:

| 設定 | フレーム/秒 | 無音時RMS | 判定 |
|---|---|---|---|
| MASTER 各種 | 16k〜17k | 17155〜17880 | 全滅（自分のクロックで無意味なビットを読むだけ） |
| SLAVE I2S 16bit | 32,427 | 239.9 | 静かだが**レートが2倍**（32bitスロットを2回に割っている） |
| SLAVE I2S 32bit | **16,213** | 256.2 | **正解** |
| SLAVE MSB | — | 23000超 | 全滅 |

**RMSだけで判断してはいけません。** 一様乱数のRMSは 32768/√3 ≒ 18918 で、これに近い値は
音声ではありません。逆に静かに見えても実測フレームレートが 16kHz から外れていれば
スロット幅が合っていません。`scan2` はこの両方を見て選びます。

| 信号 | GPIO | XIAOピン | 向き |
|---|---|---|---|
| BCLK | 8 | D9 | |
| WS / LRCLK | 7 | D8 | |
| DOUT | 43 | D6 | ESP32 → ReSpeaker（スピーカー） |
| DIN | 44 | D7 | ReSpeaker → ESP32（マイク） |
| MCLK | 9 | D10 | 公式サンプルが未使用のため既定では出さない |

**I2C(D4/D5) とは衝突しません。** OLEDと共存できます。

フォーマットは **16kHz / 16bit / ステレオ**。マイクはステレオで届くので ch0 を使い、
スピーカーへはモノラルを左右へ複製して書きます。

### 会話の手順

```
wifi      # Wi-Fi接続
c         # DOへ接続
1         # 話し始める（録音してDOへ送る）
          # ... 喋る ...
2         # 話し終わる（audioStreamEnd を送る）
```

BOOTボタンでも `1`/`2` を交互に切り替えられます。`au` で音声の状態を確認できます。

`clientContent` + `turnComplete` ではなく **`audioStreamEnd`** を使うこと。VADが発話中と
認識していると前者は無視されてハングします（`wrapper.py` で確定済みの知見）。

### 設計上の注意（いずれも実機で踏んだ問題）

- **バイナリフレームは無条件に音声として扱う。** 中身を覗いて振り分けてはいけない。
  PCMデータの先頭バイトがたまたま `{` (0x7B) になることは256分の1で起きる。実機で
  1フレーム誤判定して音が欠けた。制御は必ずテキストで来ることをDO側で保証している。
- **音声フレームは4KB以下**である必要がある。`links2004/WebSockets` は
  `WEBSOCKETS_MAX_DATA_SIZE = 15KB` 超を受け取ると中身を読まず `close(1009)` する。
  DO側で刻んでいる。「文字起こしは届くが音声が来ずに切断」という症状で発現した。
- **受信中は描画を間引く。** OLEDの全面転送は約29msブロックする。20FPSのままだと
  時間の6割を描画に取られ、`ws.loop()` が呼ばれず受信を落とす。再生中は8FPSへ落とし、
  `ws.loop()` は1周あたり8回まわす。
- **再生は専用タスク + リングバッファ**で行う。Gemini は応答音声を実時間よりずっと速く
  まとめて送ってくるため、受信した場所から直接 `i2s_write` すると DMA が空くまで
  ブロックして OLED の描画が止まる。
- **送るものが無くても無音を書き続ける。** TXを止めるとDMAが枯渇し、条件によっては
  直前の内容を繰り返して大音量のノイズになる。
- 再生バッファは **PSRAM があれば 512KB（16秒）**、無ければ 48KB（1.5秒）に縮小する。
- **エコーガード**: 再生中はマイクを送らない。送ると自分の声で Gemini が割り込み判定して
  会話が破綻する。ReSpeaker Lite のハードウェアAECが効けば不要になるはずの暫定措置。
- マイク読み出しは**タイムアウト0の非ブロッキング**。描画を止めないため。
- **出力は音量を絞る（既定35%）。** ReSpeaker Lite の出力はアンプ経由。イヤホンを直結すると
  非常に大きな音になるため、耳に着けたままテストしないこと。

### 顔と会話の同期

`StateMachine` は IDLE→LISTEN→THINK→SPEAK の一本道で途中を飛ばせない。一方 Gemini は
自前のVADで勝手にターンを進めるため状態が食い違う（LISTENが10秒でタイムアウトしてIDLEに
戻った後に応答音声が届く、など）。`driveTo()` で必要なイベントを順に注入して追いつかせる。

| Geminiからの通知 | 顔 |
|---|---|
| `speechState: SPEECH` | LISTEN |
| `speechState: NON_SPEECH` | THINK |
| 音声フレーム到着 | SPEAK |
| 再生完了 + turnComplete | IDLE |

**実用上、`2`(audioStreamEnd) を押す必要はない。** Gemini のVADが発話終了を検知して応答を
始める。`1` で録音を開始すれば、あとは自然に会話が続く。

### ReSpeaker Lite のファームウェア

ReSpeaker Lite には **I2S版と USB版**のファームがあり、**USB版では I2S から音が出ません**。

USBオーディオデバイスとして Windows に現れるかどうかで判別できます（現れなければ I2S版）。
確実に確認するには XMOS側のUSB-Cポート（3.5mmジャック寄り）を繋いで `dfu-util -l`。
Windowsではドライバが当たっていないため Zadig で WinUSB を入れる必要があります。

```bash
dfu-util -R -e -a 1 -D respeaker_lite_i2s_dfu_firmware_v1.0.9.bin
```

**`ch0-asr/ch1-mww` ファームについての訂正**（2026-07-26に一次情報で確認）:

`v1.1.0_ch0-asr_ch1-mww` という派生ファームは存在するが、**ウェイクワードを検出しない**。
ch1は「外部のMicro Wake Wordエンジンに向いた処理をした音声」を出すだけで、判定そのものは
ESP32側でやる必要がある（ESPHomeの microWakeWord コンポーネント用という位置づけ）。
「載せ替えれば自前のTinyMLが不要になる」というのは誤り。

### 2026-08-02: XMOS が起動しなくなった（音声全滅）

つまみのAS5600ファームを書き込んだ日の午後、**XMOS (XU316) が起動しなくなった。**
ESP32はI2Sスレーブでクロックは全部XMOSから来るため、音の入出力が全滅している。

**症状と証拠**（どれも単独で再確認できる）:

| 見たもの | 結果 | 意味 |
|---|---|---|
| `au` | 再生キューが溜まったまま**再生済み0サンプル** | I2Sが1バイトも流れていない |
| `scan2` | SLAVE全設定で**0フレーム**、MASTER読みは常にFFFF | BCLK/WSもDIN(マイク)も来ていない |
| `v8` / `v9` | WS(D8)=0mV / BCLK(D9)=0mV | クロック線が物理的に沈黙 |
| `creg`（電源再投入後） | P0 0x3F=**0x14（AIC3204の初期値）** | **XMOSが起動時のコーデック設定を書いていない** |
| XMOS側USB-CをPCへ | **列挙されない**（過去はVID_2886&PID_0019が見えた記録あり） | XMOSのUSBスタックも動いていない |

**切り分けで消したもの**（⚠ ここで消せたのは「**今の症状を維持している要因**」だけ。
「**壊した原因**」の免罪ではない — 作業中に壊れたものは配線を抜いても直らないため、
最小構成テストは原因の切り分けにならない。2026-08-02 訂正）:

- **給電構成ではない** — XIAO側給電・XMOS側給電・両方給電（バッテリー併用）すべてで同じ
- **治具の配線ではない** — AS5600の5本を全部抜いた最小構成・冷間起動でも 0x3F=0x14 のまま
- **ESP32側ソフトではない** — コーデック設定を書くのはXMOSで、その書き込み自体が無い
- **ケーブル/PCポートではない** — 同じケーブルでCOM3(XIAO)は正常に使えている

**原因は不明**。時系列の相関（ESP32ファーム書き込みリセットの轟音が最後の音）は事実で、
書き込みリセット中のピン不定によるI2S線のバス競合や、治具の配線作業時のダメージは
**否定できていない**。偶発的な部品故障とも矛盾しない。以前の記録が「ESP32側ソフトでは
ない＝書き込み作業は無関係」と読める書き方だったのは上記の混同によるもの。

**時系列**: 書き込み直前まで音は出ていた（書き込みリセット時にROMブートログの轟音が
出た＝その瞬間はXMOSがクロックを出していた証拠）。その轟音が最後の音。
因果は特定できていない（轟音はXMOSより下流で鳴るので、音自体がXMOSを壊す経路は
考えにくい。※「組立時の3V3-GND短絡の遅発」説は記録誤りにつき撤回 — 短絡は
実際には起きていない。ユーザー確認 2026-08-02）。

**2026-08-02 深夜の再検証**(冷間起動とUSB抜き挿し計7回+αで再現確認):

- **XMOSは完全沈黙ではなく「起動して0.5〜3秒で必ず死ぬ」**。XMOS側USB-Cを挿すと
  VID_2886&PID_0019 が列挙されるが、0.5秒または2.5〜3秒で切断する(7回中7回死亡、
  生存時間はこの2グループに分かれる)。データ線のある別ケーブルでも同じ
- **死ぬまでの進み方が毎回違う**。事故時と再検証初回の冷間起動はコーデック全初期値
  (0x3F=0x14)のままだったが、別の冷間起動では**コーデック初期化の大半を完走**していた
  (P0 0x1B=0x30, P1 0x09=0x3C, 出力経路0x08。DAC電源ONの手前で死亡)
- **抜き挿しを繰り返すと悪化する**(後半は3連続で0.5秒側)。固定点で死ぬファームの
  バグではなく、マージナルなハード(はんだクラック・電源レール・シリコン損傷)の振る舞い。
  なお**基板は無改造・短絡事故も無し**(ユーザー確認 2026-08-02。過去記録の
  「はんだブリッジ」「3V3-GND短絡」はどちらも誤記録)
- 落ちた後は挿しっぱなしでも自然に再列挙しない(ブートループではない)

**復旧手段は無い**: ReSpeaker Lite に Safe Mode・リカバリピン等の公式手順は存在せず、
DFUはUSB列挙が前提。列挙は最長3秒でドライバのバインドすら間に合わず、ソフトからは
触れない(JTAGで触るにはxTAGが要る)。**ボード交換になる。**

**生きているもの**: ESP32(XIAO)・OLED・AS5600・I2Cバス全デバイス・つまみファーム一式。
つまみの角度→%→ゲインは実測合格済みで、耳での音量確認だけが保留
（[docs/KNOB-ENCODER.md](../../docs/KNOB-ENCODER.md)）。

**次のボードで必ずやること**（**新しいXIAOを使うと決定** 2026-08-03。
NVSが空なので初期設定は一式やり直し。旧XIAOは設定ごと予備として保管）:

1. **ファームをUSBで初回焼き**（`pio run -e xiao_esp32s3 -t upload`。
   OTA待受を載せるまではWi-Fi書き込み不可）
2. **Wi-Fi設定**（起動時に自動で設定モードに入る。QRから、またはシリアルで `ssid`/`pass`）
3. **I2S版ファームか確認**（この節の冒頭。USBオーディオとしてPCに見えたらUSB版なので焼き替え）
4. **Usr-D2 の導通**（上の「Usrボタン」の節。現機はピンを穴に通してぶら下げているだけ・はんだ付け無し）
5. シルクを読んでから挿す・初回は `s` で全アドレスが出るまで疑う（OLED/AS5600で2例あり）
6. **`knobzero` 取り直し**（ゼロ点は新XIAOのNVSには無い）→ 治具で 0/¼/½/¾/最大 の単調確認
7. 保留中の**耳確認**: `beep2` を ¼ と 最大 の2点で（これでAS5600移行が完了）

さらに **DFU版は48kHzのみ**（`respeaker_lite_i2s_dfu_firmware_48k_v1.1.0_ch0-asr_ch1-mww.bin`）。
現構成は16kHz（Geminiの入力仕様と一致）なので、載せるとマイク側と再生側の両方に
レート変換が必要になる。16kHzの ch0-asr/ch1-mww は factory firmware のみで、
DFUとは書き込み手順が違う。

結論: **ウェイクワードのためにこのファームを入れる必要はない**。判定はどうせESP32側なので、
まず既存の16kHz ch0 の音声で作る。ch1は「認識精度が上がるかもしれない改善案」であって
前提条件ではない。使うときは `KATANORI_MIC_CHANNEL` で切り替える。

## OTA: Wi-Fi経由のファーム更新（2026-08-03 実機確認済み）

筐体に封入した後もファームを直せるようにする仕組み（TODO 2章。優先2位だった）。
ArduinoOTA を使い、Wi-Fiが繋がると自動で待受が始まる。

```bash
pio run -e xiao_esp32s3_ota -t upload
```

- **初回だけはUSBで通常envを焼く**こと（OTA待受コードが乗っていない機体は受けられない）
- `katanori.local` が引けない環境では `platformio.ini` の `upload_port` を機体のIPに
  （IPはシリアルの `ota` で出る）。合言葉は `--auth=katanori`（`KATANORI_OTA_PASSWORD`）
- 転送は反対側のOTAスロット（default_8MB.csv の app0/app1、各3.3MB）へ書かれ、
  **MD5検証に通ってから起動先が切り替わる**。途中で切れても現行ファームのまま
- 転送中はOLEDに UPDATING と進捗バーが出る（実装済み。初回OTA時はOLEDが見えて
  おらず**目視は未確認**。次のOTAで確認する）。終わると自動再起動
- シリアル: `ota`（状態表示）/ `otadis`（待受の無効/有効。計測中の誤爆防止用）

**届く条件に注意**: 疑似電源OFF（つまみOFF位置）では自動接続ごと止まるので**OTAも届かない**。
更新するときはつまみをONにしておく。卓上でつまみ未接続のときはピン浮きで疑似電源OFFに
入るため、先に `knobdis` を打つ（実機で2回踏んだ）。

実測（2026-08-03 深夜）: USB初回焼き → Wi-Fi越しに同一ファームを再送（63秒・約1.2MB）→
自動再起動 → 新スロットで起動 → 待受再開、まで一巡を確認。
遠隔（インターネット越し）の更新は未実装で、DOの認証（TODO 4章）と合わせて設計する。

## Stage 4: Wi-Fiプロビジョニング

Wi-Fi未設定なら起動時に自動で設定モードへ入ります。手動なら `prov`、または
**BOOTボタン3秒長押し**。抜けるのは `provoff` か、設定モード中の3秒長押し。

| 操作 | 動作 |
|---|---|
| BOOT短押し（通常時） | 話し始め / 話し終わり |
| BOOT短押し（設定モード中） | QR画面 ⇄ 文字画面 |
| BOOT3秒長押し | 設定モードの開始 / 終了 |

### 画面

QRは Version2(25モジュール)を1モジュール2pxで 50×50px、上下7pxがクワイエットゾーン。
右の余白に文字を置きます。

**時間で自動切り替えしてはいけません。** QRの読み取りには数秒かかることがあり、
その最中に画面が変わると失敗します。ボタンによる手動切り替えにしてあります。
また**変化があったときだけ描き直します**。全面転送(約29ms)が読み取りの邪魔になるため。

0.96インチでは 4x6 / 5x7 ドットのフォントは実用になりませんでした（実機で確認）。
文字画面は全幅を使って 9x15 で描いています。

### 実装順序が重要

`Provisioning::begin()` の順序を間違えると **APがスマホのWi-Fi一覧に出ません**。

```
1. WiFi.disconnect()   STAの再接続を止める（チャンネルが動いてAPが安定しない）
2. refreshScan()       AP起動より先にスキャンを済ませる
3. WiFi.softAP()       最後にAPを立てる（チャンネル固定）
```

`WiFi.scanNetworks()` は数秒チャンネルを掃くため、**AP起動後に呼ぶとその間
ビーコンが止まり**、一覧に現れません。実機で踏みました。

### キャプティブポータルを自動で開かせる

- **302リダイレクトではなく「200 + ポータル本体」を返す。** AndroidもiOSも
  「期待した応答(204 や `<SUCCESS>`)が返ってこないこと」でポータルを判定する。
  リダイレクトだと端末によっては追随しない。
- **スキャン結果をキャッシュする。** 端末は検出用URLを何度も叩いてくる。その都度
  `WiFi.scanNetworks()`（1回数秒）を回すと、端末側のタイムアウトに間に合わない。
- 検出用の既知URL（`/generate_204`, `/hotspot-detect.html`, `/ncsi.txt` 等）も
  明示的に拾う。

### 承知のうえの弱点

設定用APは**開放（暗号化なし）でページもHTTP**です。入力されたWi-Fiパスワードは
設定中の数分間、近くの第三者から傍受されうる状態になります。市販IoT機器でも一般的な
方式ですが、弱点であることは変わりません。設定ページにも明記しています。

## 起動時の轟音とその対策

**ESP32-S3 の GPIO43 は UART0 の TX であり、この構成では I2S DOUT でもあります。**
リセット直後、ROMブートローダが 115200bps で吐くブートログがそのままオーディオとして
増幅され、耳を痛めるレベルの音になります。アプリが走る前の出来事なのでソフトでは防げません。

対策は **ESP32 がリセットされてもコーデックはリセットされない**（別電源）ことを利用します。

- ReSpeaker Lite の音声コーデック **TLV320AIC3204 (I2C 0x18)** を直接ミュートする
- **普段はミュート、鳴らすものがあるあいだだけ解除**。この状態がリセットをまたいで保持される
- DACデジタル音量を -63.5dB（page0 reg 0x41/0x42）とミュートビット（reg 0x40 D3/D2）の二段構え

### 開け閉めは1か所だけ（`pumpOutputGate()`）

`main.cpp` の `pumpOutputGate()` **だけ**がコーデックを開け閉めします。判断基準は
「再生キューに音があるか」の一点です。

以前は再生経路ごとに `setOutputMute()` を呼んでいました（応答再生・割り込み・
ターン終了）。経路が増えるたびに閉じ忘れの穴ができる作りで、起動アナウンスを
足した時点で**電源を入れるだけで自動的に開く経路**が生まれ、実際に事故になりました
（開いたまま電源を抜く → 次の起動でROMブートログが轟音）。

再生経路側でミュートを触らないこと。`announce()` のように「先にキューへ積んで、
開けるのはゲートに任せる」順にすれば、音が出ていないのに開いている時間も作らずに済みます。

手動の `unmute` はゲートを一時停止します（そうしないと鳴っていない状態として
すぐ閉じられ、スピーカー単独の切り分けができない）。**`mute` で必ず戻すこと。**
`beep` / `beep2` はスピーカー単独テストなので自分で解除します（ミュートの検証には
使えません）。

**残る穴**: 再生中にクラッシュ・電源断・リセットが起きると、解除された状態が残って
次の起動でROMブートログが流れます。ゲートは窓を「鳴っているあいだ」まで狭めますが、
ゼロにはできません。完全に潰すならスピーカー線に物理スイッチが確実です。
**喋っている最中に電源を抜かないこと。**

### モニタの開閉で再起動するのを止める

ネイティブUSB(USB-Serial-JTAG)は DTR/RTS の変化をリセットとして解釈します。
`platformio.ini` の `monitor_dtr = 0` / `monitor_rts = 0` で止まります。

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| 画面が真っ暗 | まず `t` で自己診断。それも真っ暗なら配線側、パターンが出るなら転送側の問題 |
| `[I2C] no devices found` | SDA/SCL/VCC/GND の配線と OLED への給電を確認。ソフトの問題ではありません |
| `スキャンできませんでした (戻り値 -2)` | `WiFi.scanNetworks()` の負値は「APが無い」ではなく失敗。接続の再試行中はスキャンを開始できないので、先に `WiFi.disconnect()` する |
| 設定モードのAPが一覧に出ない | AP起動後にスキャンしていないか確認（上記の実装順序） |
| 書き込みのたびに轟音 | コーデックが解除されたまま電源が切れた状態。スピーカーを耳から離して一度起動すれば `setup()` 冒頭でミュートに戻る。`unmute` を打ったあとは必ず `mute` |
| 画像が横に2ピクセルずれる / 端が回り込む | コントローラが SSD1306 ではなく **SH1106** の可能性。`U8G2_SH1106_128X64_NONAME_F_HW_I2C` に差し替える |
| `0x3C` ではなく `0x3D` が見つかる | `platformio.ini` の `build_flags` に `-DKATANORI_OLED_ADDR=0x3D` を追加 |
| I2Cピンが違う | 同様に `-DKATANORI_I2C_SDA=<n> -DKATANORI_I2C_SCL=<n>` を追加 |
| 顔が8ピクセル単位で左右反転する | `-DKATANORI_DISPLAY_BIT_REVERSE=1` を追加（MSB/LSB順の差異を吸収） |
| `PSRAM が見えていません` | `board_build.arduino.memory_type = qio_opi` が効いているか確認。Stage 3 で必須 |
| シリアルに何も出ない | ネイティブUSBのため、モニタを開き直すか RESET を一度押す |

## Stage 3 に向けたメモ

- `Esp32Hal::getMicLevel()` は現在ダミーのLFO（`KATANORI_FAKE_MIC`）。I2S入力の実測ピークに差し替える。
- Gemini の応答は 24kHz、ReSpeaker Lite の I2S は 16kHz。**リサンプルは DO 側でやる**方が実機は楽。
- base64+JSON は ESP32 には重いため、DO にバイナリフレーム受け口を追加してから着手すること。
- スピーカー出力は ESP32 → I2S → ReSpeaker Lite の DAC 経由にする（AECを効かせるため）。

`main_esp32_skeleton.cpp` は移植前の参考コード（`#if 0`）で、`src/main.cpp` に置き換わっています。
